# ADR-0001 — goal.md é neutro em relação ao runtime de goal loop

## Contexto

Existem dois runtimes de goal loop instalados nesta máquina, com semânticas de
parada diferentes:

- **Codex CLI** — `~/.codex/goals_1.sqlite`, tabela `thread_goals`, com status
  persistido em `active | paused | blocked | usage_limited | budget_limited |
  complete` e `token_budget` por goal. Há execuções GWD já concluídas
  (`"implementar o work-item de acordo com o WORKFLOW.md"` → `complete`).
- **Hermes** — `hermes_cli/goals.py`, laço Ralph: após cada turno um modelo
  juiz decide se o objetivo foi satisfeito; `DEFAULT_MAX_TURNS = 20`; falha do
  juiz é *fail-OPEN* (continua). Não há status `blocked` persistido.

## Decisão

`goal.md` não pode depender de nenhum recurso exclusivo de um runtime. O
contrato de parada é **textual**: uma frase-sinal emitida na resposta do turno,
legível tanto por um juiz LLM quanto por um humano lendo o transcript.

## Consequências

- Nenhuma instrução do documento pode assumir `token_budget`, transição de
  status ou tabela SQLite.
- A frase-sinal de parada precisa ser inequívoca o bastante para que um juiz
  LLM não a confunda com objetivo cumprido — o modo de falha do Hermes
  (fail-OPEN) é o pior caso a ser projetado.
- Ganchos específicos de runtime, se desejados depois, entram como apêndice
  opcional, nunca no corpo normativo.

## Alternativas rejeitadas

- **Mirar só o Codex CLI**: ancoraria a parada em `status=blocked`, mais
  robusto, mas inutilizaria o documento no Hermes.
- **Mirar só o Hermes**: sinal de parada mais frágil e sem uso comprovado do
  usuário para GWD.
