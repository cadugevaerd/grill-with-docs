# ADR-0001 — A documentação do ponytail vive neste repositório; o core não edita CLAUDE.md/AGENTS.md de consumidor

## Contexto
Este repositório tem `CLAUDE.md` e não tem `AGENTS.md`. O `init` do grill-with-docs fixa apenas `WORKFLOW.md`, `.specify/memory/constitution.md`, `goal.md` e o bundle em `.grill/`; nunca escreveu nos arquivos de instrução do agente de um projeto consumidor. O ponytail já publica o próprio texto de `AGENTS.md`, que o consumidor pode copiar. Evidência verificada em sessão (R-0001).

## Decisão
A informação sobre o ponytail entra no `CLAUDE.md` deste repositório e num `AGENTS.md` novo aqui (dogfooding). O projeto consumidor recebe a exigência pelo `preflight` (`dependencies.json`) e pela documentação do plugin (`SKILL.md`, `README.md`); o core continua sem tocar `CLAUDE.md`/`AGENTS.md` de terceiros.

## Opções e custos
- **A (escolhida): só este repositório.** benefício: sem nova política de escrita fora de `.grill/`, sem migração; **custo:** consumidor precisa documentar o ponytail por conta própria.
- **B: materializar seção no consumidor via `init`.** benefício: onboarding uniforme; **custo:** política nova de escrita em arquivo humano, marcador versionado, no-clobber, teste de idempotência e migração — reversão cara porque todo consumidor já teria a seção.
- **C: só no consumidor.** benefício: nenhum; **custo:** este repositório deixaria de comer a própria comida.

## Consequências
- `CLAUDE.md` ganha seção sobre o ponytail na stack; `AGENTS.md` nasce aqui com o mesmo conteúdo essencial para o Codex.
- O contrato do core sobre o que `init` escreve permanece intacto.
- Se um dia o consumidor precisar de materialização, é work item novo, não extensão deste.
- Emenda (R-0005, DQ-0005): a ativação por projeto entra no mesmo escopo "só este repositório": `.claude/settings.json` versionado com `enabledPlugins["ponytail@ponytail"]=true`. O preflight continua verificando apenas instalação; Codex não tem enable/disable e não precisa de nada.
