## Contexto

O observer de apresentação só promove `installation=present` quando a listagem nativa traz `installPath` absoluto e `version`. O `claude plugin list --json` traz os dois. O `codex plugin list --json` 0.154.0 traz `pluginId`, `name`, `marketplaceName`, `version`, `installed` e `enabled`, mas nenhum caminho, e o Codex não tem outro subcomando que exponha o caminho (`codex plugin` oferece apenas `add`, `list`, `marketplace` e `remove`). Por isso toda entrada GWD no Codex falha fechada com `STYLE-DEPENDENCY-UNDETERMINED`, mesmo com a cópia aprovada instalada.

## Decisão

No runtime Codex, o caminho da instalação é derivado de campos da própria listagem nativa, `<CODEX_HOME>/plugins/cache/<marketplaceName>/<name>/<version>/`, e só é aceito quando a entrada nativa declara `installed=true`, o diretório existe e o `skills/i-have-adhd/SKILL.md` dentro dele tem o hash aprovado pela policy. Qualquer campo ausente, diretório inexistente ou hash divergente mantém `undetermined`. O caminho do Claude (`installPath`) não muda.

## Alternativas rejeitadas

- Esperar o Codex publicar `installPath`: bloqueia C1/C2 sem prazo e sem controle deste projeto.
- Ler o cache sem a listagem nativa: perde a prova, dada pelo próprio harness, de que o plugin está instalado e habilitado.

## Consequências

- O comentário que proíbe "adivinhar caminho ausente da saída nativa" passa a ter uma exceção nomeada: o caminho não é adivinhado, é composto de campos nativos e depois confirmado em disco e por hash.
- O layout do cache Codex passa a ser uma dependência declarada. Se o Codex mudar esse layout, a entrada volta a falhar fechada, sem aceitar nada por engano.
- O mesmo layout já é consumido pelo preflight do Ponytail. Esta decisão reaproveita esse padrão, sem criar um novo.
