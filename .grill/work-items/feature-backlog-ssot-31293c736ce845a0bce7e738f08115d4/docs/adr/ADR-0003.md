# ADR-0003 — BL aberto nasce in_progress no backlog operacional

## Contexto

O backlog de decisão usa `open | resolved | superseded`, com `resolved` e `superseded` terminais. O backlog operacional usa `open | in_progress | done | cancelled | merged`. O plano original assumia o mapa direto `resolved → done`.

A FSM real foi medida exaustivamente, os 25 pares, em banco descartável com `backlogctl 2.4.0`:

| de \ para | open | in_progress | done | cancelled | merged |
|---|---|---|---|---|---|
| **open** | ok | ok | **não** | ok | não |
| **in_progress** | ok | ok | ok | ok | não |
| **done** | não | não | ok | não | ok |
| **cancelled** | ok | não | não | ok | não |
| **merged** | não | não | não | não | ok |

`open → done` é ilegal, o que refuta o mapa do plano original. Dois outros fatos foram verificados no mesmo experimento: `item add --status STATE` aceita qualquer estado como snapshot inicial, inclusive `in_progress` e `done`, porque não é transição; e `item reconcile-status`, único caminho que ignora a FSM, exige `--confirm` e sua própria documentação o proíbe como transição normal ou atalho de migração.

Verificou-se também que o backlog operacional aceita itens duplicados: um `item add` repetido com título e descrição idênticos criou um segundo item. Não há guarda no armazenamento.

## Decisão

Um `BL-NNNN` aberto cria o item já em `in_progress`, via `item add --status in_progress`. A partir daí `resolved → done` e `superseded → cancelled` são transições legais e diretas, ambas em um único passo.

O estado `open` do backlog operacional não é usado pela ponte.

## Opções e custos

- **A: nascer em `in_progress` (escolhida):** uma transição por mudança de estado, nenhum estado falso gravado; **custo:** um BL aberto aparece como `in_progress` no `backlog list`, então quem filtra por `open` não enxerga decisões adiadas.
- **B: nascer em `open` e fazer `open → in_progress → done` ao resolver:** preserva o `open` visível; **custo:** grava no histórico do backlog um `in_progress` que durou milissegundos e nunca existiu, o que atrita com a cláusula Evidência antes de afirmação.
- **C: usar `item reconcile-status` para saltar a FSM:** um passo só; **custo:** proibido pelo contrato do próprio backlog para este uso, e exige confirmação humana a cada chamada, o que inviabiliza automação.

## Consequências

- A ponte nunca emite `open` e nunca usa `merged`.
- `superseded` mapeia para `cancelled`, que no backlog admite volta para `open`; o backlog de decisão é mais estrito e trata `superseded` como terminal. A assimetria é permissiva e inofensiva, mas o gerador nunca deve explorá-la.
- `done` só admite `done` ou `merged`, o que casa com `resolved` ser terminal.
- Como duplicatas passam sem erro no armazenamento, a deduplicação por `(work_id, BL-NNNN)` é inteiramente responsabilidade do gerador; um bug ali produz itens repetidos silenciosamente, e a migração precisa ser idempotente por construção própria.
- Consultas humanas ao SGD que filtram por `open` precisam saber que decisões adiadas estão em `in_progress`; isso entra na documentação.
