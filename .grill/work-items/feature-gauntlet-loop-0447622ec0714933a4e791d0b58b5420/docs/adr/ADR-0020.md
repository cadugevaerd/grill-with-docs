# ADR-0020 — Run ganha estado terminal (COMPLETE/BLOCKED); gate de ship varre só runs não-terminais

A primeira redação de FR-007 (gate de convergência de `ship`) mandava varrer **todas** as runs admitidas de um work item, pra não confiar na seleção "run mais recente" que `gauntlet-status` já usa (`sorted(runs)[-1]`, hash de admissão, não cronológico). Isso fechou o fail-open que motivou a mudança, mas abriu um problema pior: nenhuma run jamais sai do Store — `RUN_STATES` já declara `COMPLETE` e `BLOCKED` desde FASE-002, mas nenhum código hoje os alcança, e `phase-turn` nunca mexe em `work_items[...].gauntlet.runs`. Um único worker `FAILED` com orçamento de remediação esgotado em qualquer run passada, de qualquer fase anterior do mesmo work item, bloquearia `ship` para sempre, em toda fase futura — sem nenhum ato humano capaz de destravar, porque FR-006 já proíbe qualquer resolução automática.

A FASE-004 resolve isso dando às runs um ciclo de vida terminal real, com dois ajustes que uma rodada de crítica seguinte encontrou na primeira tentativa desta mesma decisão: (1) `gauntlet-converge` transiciona `run.state` para `COMPLETE` quando **todo `node_id` do Execution DAG** (lido via `--dag`, o mesmo argumento que `gauntlet-converge` já recebe — não "nenhuma wave pendente no Store", condição que fecharia a run assim que a primeira wave convergesse, antes até da segunda ser declarada, travando o DAG de forma irreversível) tem um worker de lineage-head `converged: true`; essa transição exige estender `store.py`'s `run_edges` com `ADMITTED→COMPLETE` e `RECOVERY_ELIGIBLE→COMPLETE` (hoje só `RECOVERY_RECORDED→COMPLETE` existe) — uma extensão de schema explícita desta fase, no mesmo espírito das extensões que FASE-003 já fez pra `WAVE_STATES`/`node_ids`, não um comportamento que já funcionava; (2) um novo comando coordinator-only, `gauntlet-run-abandon`, permite a um humano declarar explicitamente uma run irrecuperável como `BLOCKED` — exigindo um bundle `human-authorization/v1` (o mesmo schema fechado que `attestation.py` já valida pra `ship`, reusado aqui em vez de um `--reason` de texto livre: o core não tem identidade de sessão/agente, A-002, então texto livre não distingue um humano decidindo de um agente contornando o gate de `ship` sobre uma run saudável), mint de evento append-único, nunca reversível para `ADMITTED` — o "ato humano" que FR-006 já promete. Essa barreira é honestamente **atribucional, não preventiva**: `attestation.py` documenta o próprio bundle como "accepted but never inspected" pela cadeia que dá força real ao gate de `ship` (resolution→dispatch→invocation→step-output) — `abandon` não tem essa cadeia, não sendo um dos 11 passos. O ganho real é duplo: exige construção deliberada de um documento específico em vez de texto livre, e o bundle inteiro fica gravado (verbatim, campo write-once próprio na run — não um hash, que provaria só que ALGUM bundle existiu) como registro de quem autorizou. `record_resume_decision`/`gauntlet-resume` é o precedente pra "comando que muta `run.state` sem lease nem worker", mas não pro ponto que importa mais aqui: toda mutação de run hoje (`record_resume_decision` incluído) exige que a `admission` da run alvo bata com a ativação/`base_commit` correntes — e é exatamente uma run de geração **antiga**, cujo `base_commit` não bate mais, que trava `ship` e motiva este ADR. `gauntlet-run-abandon` por isso é o único comando desta fase que deriva `base_commit` e identidade da própria `admission` já gravada na run alvo, nunca da ativação corrente — sem esse desvio explícito, o comando seria inútil justamente no caso que ele existe pra resolver. O gate de `ship` (FR-007) varre só as runs cujo `state` **não** é `COMPLETE` nem `BLOCKED` — as duas únicas runs que legitimamente não contam mais pra convergência pendente.

**Alternativas rejeitadas**: escopar a varredura só à run mais recente (rejeitado: é exatamente o fail-open que motivou varrer todas — `run_id` não é cronológico); deixar a run permanentemente pendente sem mecanismo de "abandono" (rejeitado: é o deadlock que este ADR existe pra fechar — um sistema fail-closed sem nenhuma saída humana nomeada não é fail-closed, é travado); marcar a run `COMPLETE` automaticamente quando `ship` despacha com sucesso, sem exigir convergência prévia (rejeitado: inverteria a ordem que FR-007 exige — `ship` só pode fechar depois que a run já converge, nunca o contrário); fechar a run assim que "nenhuma wave pendente no Store" (rejeitado, era a versão original desta mesma ADR: essa condição é local ao que já foi declarado, não ao que o DAG inteiro ainda precisa — fecha a run depois da primeira wave, antes da segunda sequer existir, e `COMPLETE` sendo absorvente torna isso irreversível).
