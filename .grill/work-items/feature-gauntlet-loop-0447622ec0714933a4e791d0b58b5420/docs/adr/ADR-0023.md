# ADR-0023 — A checagem de identidade de admissão de todo comando gauntlet exclui `base_commit` — HEAD legitimamente avança durante convergência

Toda primitiva coordinator-only mutante de FASE-002/003 (`declare_wave`, `prepare_worker`, `terminate_worker`, `record_progress`, `remediate_node`, entre outras) passa por `_run_for_worker`, que recomputa a identidade de ativação a partir do estado Git corrente (`base_commit = git rev-parse HEAD`, sempre ao vivo) e a compara por igualdade total de dict contra `run["admission"]` já gravada — cinco campos, `base_commit` incluído. Até FASE-003, isso era são: nenhum comando gauntlet jamais avançava o `HEAD` do checkout de controle, então qualquer divergência de `base_commit` só podia significar deriva real (alguém commitou, resetou ou trocou de branch fora do fluxo gauntlet) — um sinal de staleness legítimo.

`gauntlet-converge` (FASE-004) quebra essa premissa de propósito: seu trabalho inteiro é integrar merges no `execution_branch`, avançando `HEAD` a cada wave convergida com sucesso. O builder da Phase 2 encontrou a consequência: depois de qualquer `gauntlet-converge` bem-sucedido, toda chamada seguinte de `gauntlet-wave-declare` (ou qualquer outro comando que passe por `_run_for_worker`) bloqueia `IDENTITY-STALE`, porque o `base_commit` recomputado do `HEAD` já avançado nunca mais bate com o `base_commit` original gravado na admissão da run — quebrando o fluxo natural declarar→executar→convergir→declarar-a-próxima-wave, que é o próprio propósito desta fase.

A FASE-004 resolve isso estendendo `_run_for_worker` (compartilhado por todo comando gauntlet mutante, não só os novos desta fase) para comparar só `_ADMISSION_IDENTITY_KEYS` — os quatro hashes de identidade de planejamento (`activation_sha256`, `work_item_sha256`, `workflow_sha256`, `config_sha256`) — já uma constante existente no módulo, hoje usada só localmente por `converge_wave`. `base_commit` sai da comparação de igualdade, mas não perde verificação nenhuma: `_require_base_commit` (já chamado por `_run_for_worker` antes da comparação) continua confirmando que o commit existe de fato no Git; o que muda é que `base_commit` deixa de ser tratado como sinal de staleness "o HEAD ainda é o mesmo de quando a run foi admitida" e passa a ser só a âncora fixa da run — a mesma leitura que `admission.base_commit` já tem em todo outro lugar do sistema (todo `workspace.base_commit` de worker precisa bater com `admission.base_commit`, nunca com o `HEAD` corrente). Os quatro hashes de identidade continuam protegendo exatamente o que protegiam: um `WORKFLOW.md`, config ou work item editados no meio de uma run em andamento ainda bloqueiam `IDENTITY-STALE`, porque nenhum deles nunca deveria mudar sob uma run em progresso — só `base_commit`, que agora tem uma razão legítima e nova para divergir.

**Alternativas rejeitadas**: manter a checagem de `base_commit` só pra comandos FASE-001/002/003 e usar uma comparação diferente só para os comandos novos da FASE-004 (rejeitado: duas semânticas de identidade coexistindo no mesmo helper compartilhado é exatamente o tipo de inconsistência silenciosa que este repositório evita — `_run_for_worker` é chamado de dez lugares diferentes, e um comando de FASE-003 declarando a próxima wave depois de uma convergência de FASE-004 bem-sucedida é um caminho real, não hipotético); deixar `admission.base_commit` da run avançar junto com `HEAD` a cada convergência (rejeitado: quebraria a invariante já estabelecida por FASE-002/003 de que todo `workspace.base_commit` de worker deve bater com `admission.base_commit` — novos workers de waves futuras passariam a nascer de uma base diferente da dos workers já despachados, tornando merges e comparações de escopo entre eles inconsistentes); não corrigir e aceitar que declarar a próxima wave depois de convergir exige um `gauntlet-run` novo a cada wave (rejeitado: um "run" de FASE-002 é uma unidade de identidade de execução contígua — fragmentar em uma run por wave destruiria o rastreamento de orçamento de remediação por `worker_id`/lineage que FASE-003 já estabeleceu por run, não por wave).
