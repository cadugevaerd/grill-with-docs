# ADR-0016 — Líder de macroetapa atesta seu checkpoint pelo verificador já existente

BL-0001(c) e a OQ-001 do precode perguntavam se a FASE-003 precisa de uma camada nova de verificação para aceitar que um líder de macroetapa (o subagente Claude despachado para `specify`, `plan`, `checklist` etc.) de fato terminou seu trabalho, ou se pode confiar cegamente no próprio líder. O sistema já resolve exatamente esse problema: `checkpoint_command` (`grill_workspace.py`) nunca aceita um passo sem antes chamar `judge_checkpoint_attestation` (`attestation.py`), que reconstrói a cadeia de campanha de sete campos e exige que o `predecessor_output` do receipt bata com o passo anterior — o próprio design existe para que nenhum passo se auto-aprove.

A FASE-003 não constrói uma segunda verificação: cada líder de macroetapa despachado por esta fase submete seu resultado como um receipt para o mesmo `checkpoint --step <macroetapa> --state complete|blocked` que já governa as 11 macroetapas desde antes da FASE-001.

"Terminal", para efeito do FR-001 (nunca despachar a próxima macroetapa antes da anterior terminar), é *apenas* `development.steps[step]` chegar a `complete` — não `blocked`. `grill_workspace.py:2564` recalcula `current_step` como o primeiro passo cuja marca **não** é `complete`; um passo `blocked` nunca avança esse ponteiro, então a run trava naquele mesmo passo até um operador o resolver e regravá-lo `complete`. `blocked` é, portanto, um estado final real de um dispatch (o líder terminou de rodar e reportou que não conseguiu concluir), mas nunca uma permissão para prosseguir — note que `verify_checkpoint_attestation` só roda no branch `state == "complete"` de `checkpoint_command` (`grill_workspace.py:2539-2556`); um `blocked` exige razão não vazia mas não passa pela cadeia de atestação, então "o coordenador aceitou seu receipt" só se aplica ao caminho `complete` — as duas ideias que BL-0001(c) pedia ("o que é terminal" e "o que acontece quando um leader bloqueia") são a mesma resposta: `complete` avança, `blocked` trava, e nenhuma outra transição existe.

O `agent-execute` worker individual (cada nó do Execution DAG despachado dentro da wave) permanece fora do mecanismo de checkpoint de macroetapa: seu término é observado pelas primitivas coordinator-only da própria FASE-002/003 (lease, journal), porque um worker não é um líder de macroetapa. Uma primeira versão desta decisão tentou resolver o checkpoint de `agent-execute` *enquanto macroetapa* fazendo o coordenador (a sessão orquestradora) montar e submeter esse receipt sozinho, argumentando que o conteúdo viria agregado de transições já verificadas pelo Store. Essa versão foi descartada: `verify_checkpoint_attestation`/`judge_checkpoint_attestation` exigem um formato de campanha de sete campos para exatamente **uma** invocação de skill canônico sob **uma** lease (`attestation.py` `_CHECKPOINT_BUNDLE_REQUIRED_KEYS`, `step_output` com `worker_lease_id`/`skill_invocation_receipt_ref`/`output_sha256` no singular) — não existe forma de expressar "N workers, N leases, N transições" nesse formato sem inventar um schema novo, e a sessão montando um bundle de uma invocação de `speckit-agent-assign-execute` que nunca rodou seria exatamente a alegação não verificada que o verificador existe para recusar.

A decisão correta é mais simples: `agent-execute` recebe seu **próprio líder subagente Claude**, exatamente como as outras dez macroetapas (FR-001, sem exceção). É esse líder — não a sessão orquestradora, não um worker do Execution DAG — quem roda o laço de wave da User Story 2 (despacha, observa e remedia os workers do DAG usando as mesmas primitivas coordinator-only que qualquer outra ação de coordenador usaria) e, ao final, submete seu próprio receipt de checkpoint pela mesma cadeia de atestação inalterada, com uma única invocação de skill (a sua própria) — encaixando perfeitamente no formato existente, sem schema novo. A sessão orquestradora só despacha esse líder e aguarda seu checkpoint, exatamente como faz para `specify`, `plan` ou qualquer outra macroetapa; ela nunca submete um receipt em nome de `agent-execute`.

**Alternativas rejeitadas**: coordenador reler e re-julgar o artefato do líder antes de aceitar o checkpoint (rejeitado: duplicaria `judge_checkpoint_attestation` sem ganho, e um segundo juiz ad-hoc teria cobertura de teste pior que o verificador já existente); líder gravar direto em `state.json` sem passar pelo CLI (rejeitado: quebraria a cadeia de campanha que impede replay/skip entre passos); tratar `blocked` como terminal-e-avançável (rejeitado: contradiz o próprio recálculo de `current_step` em `grill_workspace.py:2564` e deixaria o loop avançar sobre uma macroetapa que falhou); sessão orquestradora agregando e submetendo um receipt de `agent-execute` a partir das transições do Store (rejeitado: o formato de atestação de campanha de sete campos modela uma invocação de skill, não N transições de worker; construir esse bundle exigiria atestar uma invocação de `speckit-agent-assign-execute` que nunca rodou — exatamente a alegação não verificada que o mecanismo existe para recusar); estender `checkpoint-attestation/v1` para um formato agregado multi-lease (rejeitado por esta decisão: reabriria um schema compartilhado por todos os passos de todo item V3 quando dar a `agent-execute` um líder próprio já resolve o problema sem tocar nele).
