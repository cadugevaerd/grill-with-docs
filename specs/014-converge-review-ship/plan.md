# Implementation Plan: Convergência, Revisão e Entrega Verificável

**Branch**: `014-converge-review-ship` | **Date**: 2026-08-16 | **Spec**: [spec.md](spec.md)
**Phase**: `FASE-004` | **Delivery Unit**: `DU-004` | **Work Item**: `feature-gauntlet-loop-0447622ec0714933a4e791d0b58b5420`

## Summary

Give the coordinator's Store schema a real terminal lifecycle for a gauntlet run (`COMPLETE`/`BLOCKED`, ADR-0020) and a `gauntlet-converge` primitive that integrates each wave's successful workers back into the work item's `execution_branch`, wave by wave, with fail-closed scope/content conflict detection (ADR-0021, ADR-0022). `checkpoint --step ship` gains a single, cheap gate — every admitted run must be terminal — closing the gap between the Store's durable run/wave/worker state (FASE-002/003) and the generic 11-step checkpoint (FASE-001). A new coordinator-only command, `gauntlet-run-abandon`, is the one human act that can mark an irrecoverable run `BLOCKED`, using the same `human-authorization/v1` schema `attestation.py` already validates for `ship` (honestly a barrier that is attributional, not preventive — see Research Decisions). `review` needs no new mechanism: it is already one of the eleven macro-steps FASE-001/003 dispatch identically. This phase never resolves a conflict automatically and never pushes to a remote — those stay human acts (ADR-0002, unchanged).

## Technical Context

**Language/Version**: Python 3.10+ (standard library only)

**Primary Dependencies**: Existing `grill_workspace.py`, `grill_core.store`, `grill_core.gauntlet_runs` (extended, not replaced), `grill_core.attestation` (its `_validate_human_authorization` reused standalone by `gauntlet-run-abandon` — no change to `attestation.py` itself), local Git

**Storage**: Existing common-Git Project Store (`orchestrator.json`, chained `events.jsonl`, receipts), extending the FASE-002/003 `work_items.<id>.gauntlet.runs[*]` and `.waves[*]` records; no new store, database, or untracked authority file

**Testing**: Python `unittest` public-contract validators (new `tests/validate_gauntlet_converge_contract.py` plus extensions to `tests/validate_orchestrator_store_contract.py` and `tests/validate_gauntlet_scheduler_contract.py`)

**Target Platform**: POSIX Python CLI with Git worktree support, unchanged from FASE-001/002/003

**Project Type**: Claude/Codex plugin command-line tool

**Performance Goals**: Convergence of one wave is one Store transaction per successfully merged worker (`worker-converged`), plus one closing transaction for `wave-converged` and, if applicable, `run.completed` — not a single transaction for the whole wave, matching AC US1-3's requirement that an early conflict never reverts an already-merged sibling; a scope-overlap or content-conflict block is its own single transaction. No background process, no polling loop in the core.

**Constraints**: One JSON object on stdout per command; current activation proof before every mutable action (except `gauntlet-run-abandon`, which deliberately operates on a target run's own recorded `admission`, never the current activation — see Research Decisions); CAS/journal/receipt correlation (FASE-002 pattern, reused); scope-overlap detection uses the Execution DAG's declared `files`, never `grant.scope_paths` (ADR-0021); `COMPLETE` and `BLOCKED` are absorbing run states, so both `run_edges` and the DAG-pin field must be extended deliberately, not implied

**Scale/Scope**: A run may have any number of waves; `gauntlet-converge` processes exactly one wave per call, in the order waves were declared; this phase never regenerates or edits an Execution DAG, it only reads and pins the one a run already committed to at first real wave declaration

## Research Decisions

| Decision | Rationale | Alternatives rejected |
|---|---|---|
| Scope-overlap detection uses the Execution DAG's declared `files`, never `grant.scope_paths` (ADR-0021) | Empirically refuted that the two are ever guaranteed equal: `declare_worker` never compares `--files` against the DAG node's own `files`, and FASE-003's own contract suite already exercises a deliberate divergence (`test_worker_declare_rejects_grill_scoped_grant_even_when_dag_node_files_are_in_scope`). | Reusing `grant.scope_paths` as a durable, no-DAG-read source (the plan's own first draft) — provably unsound once the divergence was found in the shipped FASE-003 test suite. |
| Run gains a real terminal lifecycle: `COMPLETE` when every DAG node's lineage-head is `converged`, `BLOCKED` via a new human-authorized command (ADR-0020) | Without a terminal state, `checkpoint --step ship`'s new gate (FR-007) would have to scan every admitted run forever — one permanently `FAILED` worker in any past run, of any past phase, would block `ship` for the rest of the work item's life, with `FR-006` explicitly forbidding any automatic resolution. | Scoping the ship-gate scan to only the "current" run (`gauntlet-status`'s default selection, `sorted(runs)[-1]`) — refuted: that id is a lexicographic max of an admission hash, not chronological; a stale-but-incomplete run could be silently skipped (fail-open, the opposite of FR-007's purpose). |
| The DAG's content hash is pinned to the run at the moment the *first real* wave (the one that replaces the bootstrap placeholder `wave-0001`) is declared, never inferred from "the first call after this phase ships" | `run["waves"]` is never empty — every admission already seeds a placeholder wave (`WAVE_PENDING_NODE_IDS`) so the Store's own event-correlation guard has a `wave_id` to reference. Naively treating "next `gauntlet-wave-declare` call" as "first" would let a legacy run silently adopt a later, possibly-truncated `--dag` as if it were authoritative, and `COMPLETE` is absorbing — closing early on a wrong DAG has no undo. | Pinning inside `admission` — `admission` is closed, immutable across the run's whole lifetime, and is the literal input to `run_id`'s own hash; writing to it after `run_id` already exists is structurally impossible, not just inadvisable. |
| `gauntlet-run-abandon` derives `base_commit`/identity from the **target run's own recorded `admission`**, never from the currently active identity, and is explicitly exempted from FR-012's admission boundary | The whole reason this command exists is to unstick a run from an *older* generation than the one currently active (a `phase-turn` since then changed `base_commit`). Requiring current-generation identity, as every other command in this surface does, would make `abandon` useless in exactly the case FR-007/ADR-0020 need it for. | Applying the same admission boundary as every other command (`FR-012`) — refuted directly by the deadlock it would reintroduce: a stale run is, by definition, one whose `base_commit` no longer matches the active identity. |
| `gauntlet-run-abandon`'s `--reason` is a full `human-authorization/v1` bundle, not free text, and the bundle is copied verbatim into a second write-once run field (`abandon_authorization`) — not just hashed into a receipt's `output_sha256` | The core has no session/agent identity (A-002, carried from FASE-003/ADR-0019) — free text can't distinguish a human decision from an agent bypassing the ship gate over a healthy run. Reusing the same schema `attestation.py` already validates for `ship` is honestly attributional, not cryptographically preventive (`attestation.py` itself documents `human_authorization` as "accepted but never inspected" by the chain that gives `ship`'s gate its real teeth) — but it forces a deliberate, attributable act instead of a one-line excuse, and a bare hash would prove *something* existed without ever recovering who signed it. | A bare `--reason` string (the plan's own first draft) — refuted as a bypass with zero friction; a receipt-hash-only record (an intermediate draft) — refuted as unrecoverable: a digest proves existence, not authorship. |
| `last_conflict`'s identity/reason live in a new optional field on the **wave** record, written/removed by a narrow, named exception to the Store's existing newest-wave-only mutation guard — never reconstructed by probing a receipt name or body | Two receipt-probing designs were tried and both failed against the Store's actual schemas: the closed 8-key receipt body (`store.py`) has no free field for `node_ids`/`reason`, and a name built from `node_id`s can exceed `SAFE_NAME_RE`'s 128-character cap for a single long node id, let alone a multi-node scope-overlap set. A wave-level field sidesteps both — it's JSON content, not a filename or a closed schema key. | Extending the closed receipt schema (`store.py`) — the same category of change ADR-0022 rejects for the event envelope: opens precedent for every future feature to want its own field in a document six other phases already depend on staying closed. |

## Design

### Public command surface

All new/extended commands share FASE-001/002/003's boundary: current activation proof before mutation (except `gauntlet-run-abandon`, deliberately, see Research Decisions), one JSON object on stdout, coordinator-only Store authority, never a subagent invocation.

| Command | Inputs | Success | Fail-closed boundary |
|---|---|---|---|
| `gauntlet-converge` (new) | root, `--work-id`, `--run-id`, `--dag <path>`, `--wave-id` | `WAVE-CONVERGED` (with per-worker outcome), or `WAVE-CONVERGED-REUSED` for an idempotent replay of the wave that already converged (including the wave that already completed the run — see Design) | `RUN-NOT-ELIGIBLE` if the run is `BLOCKED`, or `COMPLETE` and `--wave-id` names anything other than the exact wave whose convergence completed it; `DAG-PIN-MISSING` if the run has no pinned DAG hash yet; `DAG-CONTENT-MISMATCH` if `--dag` diverges from the pin; `EXECUTION-BRANCH-UNSET`/`EXECUTION-BRANCH-MISMATCH` if the work item's `execution_branch` is null/different; `EXECUTION-TREE-DIRTY` if the coordinator's own worktree isn't clean; `WAVE-CONVERGENCE-OUT-OF-ORDER` if the requested wave isn't the next unconverged one; `INTEGRATION_CONFLICT` (reason `scope-overlap` or `content-conflict`) on the scope pre-pass or a real Git merge failure — the wave's `last_conflict` field records which. |
| `gauntlet-wave-declare` (FASE-003, extended) | (unchanged args) | (unchanged verdicts) | + `WAVE-SCOPE-OVERLAP` (FR-004b, same DAG-`files` check `gauntlet-converge`'s pre-pass uses) before any worker is prepared; + `DAG-PIN-MISSING`/`DAG-CONTENT-MISMATCH` (FR-004c) on every call after the first real wave, pinning the DAG hash on that first call. |
| `checkpoint --step ship` (FASE-001, extended) | (unchanged args) | (unchanged verdicts) | + `CONVERGENCE-INCOMPLETE` at the `--state complete` transition, after the existing step-sequence gate and before attestation, if any admitted run for the work item has `state` outside `{COMPLETE, BLOCKED}` (FR-007/FR-008). |
| `gauntlet-run-abandon` (new) | root, `--work-id`, `--run-id`, `--attestation <path>` (a `human-authorization/v1` bundle, `scope` = the target `run_id`) | `RUN-ABANDONED` (first call), or `RUN-ABANDON-REUSED` if the run is already `BLOCKED` with a byte-identical `abandon_authorization` already on record | `ABANDON-AUTHORIZATION-INVALID` if the bundle is missing, malformed, `decision != APPROVED`, or `scope` doesn't equal `--run-id`; `RUN-NOT-ELIGIBLE` if the run is already `BLOCKED` with a **different** bundle on record, or already `COMPLETE` (write-once on `abandon_authorization` means a divergent resubmission can't silently succeed nor silently no-op) — the CLI layer validates the bundle with `attestation`'s own `_validate_human_authorization` before `gauntlet_runs.abandon_run` ever runs, and translates any `AttestationError` it raises into `ABANDON-AUTHORIZATION-INVALID` (see Design); no admission-boundary check (deliberate, FR-012 does not apply); no `_require_base_commit` check on the derived `base_commit` (deliberate — a stale run's original commit may be gone). |
| `gauntlet-status` (extended) | (unchanged args) | (unchanged projection) | + `waves: [{wave_id, state, converged_count, member_count}]` (excluding the bootstrap placeholder) and, if any real wave carries `last_conflict`, the **most recently declared** one that does (never assumed to be the newest wave overall — see Design). Read-only; unchanged failure modes otherwise. |

`review` needs no new command or verdict: it is one of the eleven macro-steps already dispatched by the unmodified FASE-001/003 mechanism, at `TIER_POLICY["review"] == "large"`. A `blocked` checkpoint on it already halts `ship` via the existing step-sequence gate (`grill_workspace.py`) — FR-007 adds a second, independent reason `ship` can be unreachable (convergence), not a replacement for the first.

### Store schema extension

`grill-gauntlet-runs/v1` (FASE-002/003) gains, inside an existing run's record and inside a wave record:

```json
{
  "state": "COMPLETE",
  "admission": { "...": "unchanged, five keys" },
  "dag_content_sha256": "sha256:<hex>",
  "waves": {
    "wave-0002": {
      "state": "ACTIVE",
      "node_ids": ["T005"],
      "last_conflict": {
        "node_ids": ["T005"],
        "reason": "content-conflict",
        "execution_branch_head": "<sha40>",
        "worker_heads": {"T005": "<sha40>"}
      }
    }
  },
  "workers": {
    "T003": {
      "state": "TERMINAL", "lease": "...", "grant": "...", "node_id": "T003", "remediates": null,
      "workspace": {"worktree_key": "...", "branch": "...", "base_commit": "...", "clean": true, "converged": true, "cleanup_eligible": false}
    }
  }
}
```

`abandon_authorization` is omitted from this example on purpose: it is optional and absent on every run until `gauntlet-run-abandon` writes it — never present as `null` (that would be a different schema, required-and-nullable, with a different guard; see extension #3).

Six extensions, each independently named and scoped — none reuse an existing closed-key helper (`_closed_object`) without changing it, matching the `required`/`optional` pattern `_transition_fields` already uses for the event envelope:

1. **`run_edges` (`store.py`)** gains `ADMITTED → COMPLETE` and `RECOVERY_ELIGIBLE → COMPLETE` (only `RECOVERY_RECORDED → COMPLETE` exists today). `gauntlet-converge` drives this transition when every `node_id` of the *pinned DAG* — the run's full node set, not any per-wave count — has a lineage-head worker `state == "TERMINAL"` with its branch already merged (`converged: true` on the worker's `workspace`, extension unchanged from FASE-003's own schema). Extension #5 (wave-level `converged`) is a distinct, narrower flag that speeds up step 3/5's own bookkeeping; it is never itself the run-completion predicate.
2. **Run record gains `dag_content_sha256`** (optional, write-once): the run's `_closed_object` call (`store.py`, today the exact set `{admission, state, recovery_count, waves, workers, last_transition}`) is replaced with the `required`/`optional` style `_transition_fields` already uses for the event envelope, admitting this one new optional key. A transition guard (same mechanism that already makes `admission` immutable) accepts absent→present exactly once and rejects any further write, matching or not. Written by `gauntlet-wave-declare` exactly when it detects it is replacing the bootstrap placeholder wave (`newest_state == "DECLARED"` **and** `node_ids == WAVE_PENDING_NODE_IDS` — the second half of that conjunction does not exist in today's `expect_placeholder` calculation and must be added, or a Store-injected `DECLARED` wave with real `node_ids` — already produced by existing test fixtures — would be misread as "first").
3. **Run record gains `abandon_authorization`** (optional, write-once, same `required`/`optional` migration as #2 — one migration on the run's key set, admitting two new optional keys, each with its own write-once guard): the full 6-key `human-authorization/v1` bundle, copied verbatim by `gauntlet-run-abandon` in the same transaction that flips `state` to `BLOCKED`. Write-once here is structural, not a policy choice — `BLOCKED` is reached at most once per run.
4. **Wave record gains `last_conflict`** (optional): the wave's own key-set check (`store.py`, today the inline exact-match `set(wave) != {"state", "node_ids"}`, not `_closed_object`) becomes `required`/`optional` to admit it, and validates its four keys with the same primitives the run/worker records already use elsewhere — `node_ids`: non-empty list, each entry `SAFE_NAME_RE`; `reason`: one of the two literal strings `scope-overlap`/`content-conflict`; `execution_branch_head`, and every value in `worker_heads`: `HEX40` (the same 40-hex-char pattern `base_commit` already validates against). Separately, the Store's existing newest-wave-only mutation guard (`store.py`, currently one `or` of three conditions where `wave_id != newest_wave_id` alone already fails the whole check) is rewritten, not merely relaxed: for a non-newest `wave_id` present in both old and new snapshots, the guard now requires `state` and `node_ids` to stay byte-identical, and permits `last_conflict` **and `converged` (#5)** to differ — the other two conditions in the existing `or` (state-edge validity, `node_ids` write-once) still apply unconditionally to the newest wave, unchanged. No other field of a superseded wave becomes mutable.
5. **Wave record gains `converged`** (optional, write-once — never removable, no `true → absent` path — same `required`/`optional` migration as #4, and the same narrow newest-wave-guard exception #4 already carves out, extended to name this field too): a durable flag distinct from `state`. `state` already reaches `COMPLETE` on its own, driven by `terminate_worker` the moment every member's lineage-head worker reaches *any* terminal outcome (`_wave_would_complete`, FASE-003) — success or failure — so `state == COMPLETE` can never be used to detect "this wave's convergence closing transaction already ran"; the two facts are orthogonal and the wave-lifecycle design in FASE-003 already treats them that way (a `COMPLETE` wave can still have failed members pending remediation). `converged` is set `true` by `gauntlet-converge`, in the same transaction as the wave's *last* member's `worker-converged` transition, when every member `node_id` declared for the wave has a lineage-head worker in `state == "TERMINAL"` (the success-only outcome — `_node_ready`'s own docstring already distinguishes this from "merely any terminal-class state," and FR-001 requires "worker terminal **com sucesso**") with its branch merged. This flag is purely a **wave-scoped** bookkeeping signal for step 3's reconciliation and step 5's reuse check (a fast, durable "is this wave done" read) — it is *not* the run-completion predicate: extension #1's `run.state → COMPLETE` transition is decided the way FR-001 states it, by the DAG's own `node_id` set (every `node_id` of the pinned DAG has a `TERMINAL`-and-converged lineage-head), never by counting waves or their `converged` flags — a run can, and by FASE-003's own wave-sizing usually will, need more waves declared after the current one, and treating "this wave's flag is true" as "the run is done" would close the run after the first wave, exactly the premature-closure bug FR-001/ADR-0020 already rejected once.
6. **New `events.jsonl` categories and receipt naming (FR-010)**: `gauntlet.converge.worker-converged`, `.conflict`, `.wave-converged`, `gauntlet.run.completed`, and `gauntlet.run.abandoned` reuse the same closed event envelope FASE-002/003 already use (`store.py`'s `_transition_fields`-validated shape: `event`, `work_id`, `run_id`, `wave_id`, `base_commit`, `input_sha256`, `output_sha256`, `receipt_sha256`, required; `worker_id`/`lease_id`/`fencing_token` optional, all-or-nothing) — no new envelope field, matching ADR-0022's refusal to widen it. The two run-level events (`gauntlet.run.completed`, `gauntlet.run.abandoned`) carry no `worker_id`/`lease_id`/`fencing_token` (they're run-scoped, not worker-scoped) but still need a `wave_id` the Store guard can correlate against (`_candidate_transition` requires the named `wave_id` already exist in the run) — both name the run's current newest wave, which always exists (even the bootstrap placeholder satisfies this). Receipt names for all five follow the same literal pattern every FASE-002/003 gauntlet receipt already uses (`gauntlet-wave-declared-{run_id}-{wave_id}`, `gauntlet-worker-declared-{run_id}-{worker_id}`, `_failed_receipt_name`'s `gauntlet-worker-failed-{run_id}-{worker_id}-{failure_class}`, `gauntlet_runs.py`) — no hash, none needed: unlike `last_conflict` (ADR-0022), none of these five events ever needs to name more than one `node_id`, since node identity for a conflict lives in the wave's `last_conflict` field, never in an event or its receipt (FR-010 makes this explicit). `SAFE_NAME_RE`'s 128-character cap is the same constraint every existing receipt already respects with literal names; this phase doesn't reach it differently. Receipt `category` for all five is `"runtime"` — the one value every existing gauntlet transition already uses (`_receipt_and_event`, `gauntlet_runs.py`); this phase doesn't introduce a second category.

`WORKER_STATES`, `WAVE_STATES`, `NON_TERMINAL_WORKER_STATES`, the worker record's six required keys, and the `workspace` sub-object's six required keys (all FASE-002/003) are unchanged — `converged` already exists as a required key of `workspace` (not of the worker record itself), always seeded `False` by `prepare_worker`; this phase is the first to ever write it `true`.

### Convergence (FR-001–FR-005, FR-004b, FR-004c)

`gauntlet-converge`'s checks run in this fixed order — matching FR-001's own stated sequence ("depois da fronteira de admissão comum e antes de qualquer lógica específica de convergência") rather than putting the terminal-run shortcut first:

1. **Admission boundary (FR-012)** — the standard `gauntlet_run_admission` fronteira, unconditional, before anything else.
2. **DAG pin (FR-001/FR-004c)** — `DAG-PIN-MISSING`/`DAG-CONTENT-MISMATCH`, exactly as FR-001 requires ("depois da fronteira de admissão comum e antes de qualquer lógica específica de convergência") — **before** the terminal-run check in step 3, not after: FR-004c requires revalidating `--dag` against the pin on "every following call," with no exception for a reuse/replay call, and a `COMPLETE` run always has a pin by construction (it cannot have reached `COMPLETE` without one), so checking it first costs nothing on the reuse path and closes the gap a later check would leave open (a stale `--dag` on a replay call would otherwise report success against the wrong DAG).
3. **Terminal-run check first, then reconciliation** (not the shared `_run_for_worker` guard, which rejects `BLOCKED`/`COMPLETE` uniformly with `RUN-NOT-ELIGIBLE` and alone would break FR-005). `state == BLOCKED` always rejects `RUN-NOT-ELIGIBLE` immediately, no reconciliation attempted — an abandoned run never gains a new transaction of any kind, matching `run_edges`' own `BLOCKED → {BLOCKED}`. `state == COMPLETE` accepts *only* a `--wave-id` equal to the run's newest wave and short-circuits to `WAVE-CONVERGED-REUSED` with no branch/tree/merge work — reconciliation is a no-op here too, by construction: `run.completed` (extension #1) is only ever minted immediately after that same wave's `converged` flag (extension #5) already succeeded in the same closing chain, so a `COMPLETE` run's newest wave always already has `converged: true`. Only a **non-terminal** run (`ADMITTED`/`RECOVERY_*`) reconciles: because `transact_with_event` mints exactly one event per transaction, a wave's last member reaching `converged: true` (`worker-converged`), the wave's own `converged` flag (`wave-converged`), and the run's `state` (`run.completed`) are up to three sequential transactions within one call, not one combined transaction — a crash between them is real and reachable. Reconciliation checks, for the run's current wave only: if every dispatched member's lineage-head is `converged: true` but the wave's own `converged` flag (extension #5 — **not** `state`, which FASE-003's `terminate_worker` already drives to `COMPLETE` on any terminal outcome, success or failure, independent of convergence) isn't `true` yet, mint `wave-converged` now; then, if every `node_id` of the pinned DAG now has a converged lineage-head, mint `run.completed` now. This runs on *every* call reaching a non-terminal run — not a special "replay" branch — so an interruption between any of these transactions is closed by whichever `gauntlet-converge` call comes next, for any wave.
4. **`execution_branch`/tree state** — `EXECUTION-BRANCH-UNSET`/`-MISMATCH` (read by the `grill_workspace.py` CLI handler via the same `read_development_state` call `checkpoint`/`phase-turn` already use, threaded into `gauntlet_runs.converge_wave(...)` as an explicit parameter, the same pattern `activation_max_workers` already crosses that boundary with) *and* the CLI handler's own live check that `root`'s currently checked-out branch (`git branch --show-current`, empty on a detached `HEAD`) matches that same `execution_branch` — the same pairing `checkpoint`'s own handler already does (recorded value vs. live branch), not just the recorded value alone; a detached or mismatched control checkout blocks `EXECUTION-BRANCH-MISMATCH` the identical way — and `EXECUTION-TREE-DIRTY` for the coordinator's own worktree at `root`. This is **not** a verbatim reuse of `_exact_worktree_is_clean(root, target)` (`gauntlet_runs.py`) — that helper's own docstring promises "no tracked or untracked dirt" and takes no toggle for either; `converge_wave` needs an actual new keyword parameter on it (e.g. `include_untracked: bool = True`, default preserving today's strict behavior so `cleanup_worker`'s two existing call sites are unaffected) that this caller alone sets `False` for the dirty-gate's own tracked-only check, because the control checkout routinely carries untracked scratch/spec files (this very phase's own `specs/014-.../` directory, mid-session, is untracked and uncommitted) that must never block convergence on their own — only modifications to already-tracked content are disqualifying via this gate. The same call, regardless of that toggle, separately captures the untracked set with `git status --porcelain --untracked-files=all` (the `-uall` form this repo already uses elsewhere, `grill_workspace.py`, when it needs file-level entries — the tool's own default, `-unormal`, collapses an untracked directory into one entry like `?? specs/`, which would silently fail to match any file path a worker's diff names) — one read, serving both this gate's tracked-only check and the merge step's own pre-check below. Excluding untracked files from *this* gate doesn't make them harmless to the merge itself, so the merge step pre-checks for the collision deterministically, over the union of every wave member's diff, **once, before attempting the first merge of the wave** (not per-member inside the merge loop — the pre-pass is meant to stay a pre-merge gate end to end, per the spec's own framing of these blocks as never `INTEGRATION_CONFLICT`) — rather than trying to distinguish the failure after the fact by exit code (both untracked-overwrite and a real conflict exit `1`) or by parsing git's own locale-dependent, gettext-translated error text, which this codebase has no precedent for and would misclassify silently under any non-English `LC_ALL`: for each member, `git diff --name-only <merge-base>..<worker-branch>` against the `-uall` untracked set captured above; any overlap for any member blocks `EXECUTION-TREE-DIRTY` for the whole wave before any merge is attempted, never `INTEGRATION_CONFLICT`, which stays reserved for a merge that was actually attempted and actually conflicted on tracked content.
5. **Wave order (FR-004)** — the requested wave must be the run's next not-yet-100%-converged wave in declaration order, **except** that a wave already 100% converged (`converged: true`, extension #5) is always accepted and short-circuits to `WAVE-CONVERGED-REUSED` — this is the non-terminal-run half of FR-005/AC US1-4 that step 3's `COMPLETE`-only short-circuit doesn't cover, among the non-terminal runs that reach this step at all (a `BLOCKED`/`COMPLETE` run never falls through step 3 to here). A run still `ADMITTED` with an earlier wave fully converged and a later one still pending must let the earlier one replay, not `WAVE-CONVERGENCE-OUT-OF-ORDER`; this is safe because step 3's reconciliation already ran unconditionally earlier in *this* call, so any wave/run completion this call could close already has been by the time this step reads the flag. A wave not yet `converged` additionally requires `wave.state == "COMPLETE"` (FASE-003's own signal that every declared member reached *some* terminal outcome, success or not — `_wave_would_complete`) before this step accepts it for the merge steps below; a still-`ACTIVE` wave (a member still `PREPARED`/dispatched-but-not-yet-terminal) blocks `WAVE-CONVERGENCE-OUT-OF-ORDER` the same as an out-of-sequence one, since converging a wave mid-flight would merge a worker that might still write more commits. Any other mismatch blocks `WAVE-CONVERGENCE-OUT-OF-ORDER`.
6. **Scope pre-pass and merge set** — the wave's *mergeable* members (both for the scope pre-pass below and for the actual merges in the Convergence section that follows) are exactly the lineage-heads with `state == "TERMINAL"` — the success-only outcome, distinct from the broader `TERMINAL_WORKER_STATES` class step 5's `wave.state == "COMPLETE"` check already tolerates (`FAILED`/`STALLED`/`ORPHANED`/`CONFLICT` all leave `state`/`workspace` intact but are never merged, never `converged`, and never counted toward the wave's own `converged` flag — FR-001 requires "worker terminal **com sucesso**", and the spec's own Edge Case requires two `FAILED` siblings in one wave to never reach `converged`; a `DECLARED` worker with `workspace: None` is excluded the same way an undispatched `node_id` is, for the same reason: nothing to merge or fingerprint). The pre-pass runs over this mergeable set, using the pinned DAG's `files`, not `grant.scope_paths`. A hit blocks the whole wave, writing `last_conflict = {node_ids: <every overlapping mergeable node>, reason: "scope-overlap", execution_branch_head: <current head>, worker_heads: {<each such member>: <its branch head>}}` (all four keys populated for schema uniformity even though, per FR-002, this reason never recomputes on retry — the `files` it depends on is pinned and immutable) and converges nothing. A reentry that blocks with fingerprints identical to the wave's existing `last_conflict` re-blocks as a pure read — it does not mint a duplicate event (`_recover_pending_transition_locked` already rejects a repeated identical semantic event as `STATE_DIVERGENCE`, the same pre-existing constraint `record_progress` already lives with); only a fingerprint that actually changed triggers a new transaction. A wave whose mergeable set is smaller than its full `node_ids` (some lineage-head permanently `FAILED`/`STALLED`, remediation budget spent) can still merge everything mergeable, but its `converged` flag (extension #5) requires *every* declared `node_id` to have a `TERMINAL` lineage-head — so such a wave never sets `converged: true`, matching the spec's Edge Case exactly (permanently incomplete, `ship` blocked until `gauntlet-run-abandon`).

**Transaction shape.** Matching AC US1-3 (a conflict on one worker never reverts an earlier successful merge in the same call), each worker's merge is its own Store transaction (`worker-converged` event, `converged: true`) — a wave with five members that all merge cleanly mints five transactions, not one. In the normal, uninterrupted case, `converge_wave` closes the chain inline, within the same call: immediately after the transaction for the wave's *last* member, it checks whether the wave is now fully converged and, if so, mints `wave-converged`; then checks whether the run's whole DAG is now fully converged and, if so, mints `run.completed` — two more transactions, sequential, same call, no waiting for a later invocation. Step 3's reconciliation exists only for the abnormal case: if the process is interrupted after the last `worker-converged` transaction but before `wave-converged`/`run.completed` complete, the *next* `gauntlet-converge` call for this run (whichever wave it targets) closes the gap before doing anything else, because step 3 runs unconditionally at the top of every call. `recover_pending_transition(root)`, called at the top of `converge_wave` the same way every other mutating primitive (`declare_wave`, `cleanup_worker`, `record_resume_decision`) already opens with it, recovers a single *in-flight* Store transaction (one write interrupted mid-flight) — a different, narrower guarantee than step 3's reconciliation, which closes gaps *between* whole completed transactions.

Mergeable members (step 6's definition) are merged one at a time, alphabetically by `node_id`, into `execution_branch`, each its own transaction (Transaction shape, above); a worker whose branch has no commits beyond `base_commit` counts as a trivial success (`converged: true` on its `workspace`, no new commit). A real Git conflict blocks just that worker: before retrying, `gauntlet-converge` compares the wave's existing `last_conflict` (if `reason == "content-conflict"` and it names this same `node_id`) against the worker's *current* branch head and the *current* `execution_branch` head — identical to both fingerprints means nothing has changed since the last block, so it re-blocks immediately without attempting the merge again; either fingerprint differing means new state exists, so the merge is attempted fresh. On a fresh failure, `last_conflict` is (re)written with the current heads, and the failed attempt is atomically reverted (`git merge --abort`-equivalent) — prior successful merges earlier in the same call stand, never rolled back. No further member of the wave is processed until the block clears. A member whose merge succeeds after a prior `content-conflict` block removes `last_conflict` from the wave in that same transaction — presence/absence of the field is always current, never stale, matching FR-011's "absence means resolved." Once every mergeable member of the wave has been processed (merged or already `converged` from an earlier call), the closing chain in the Transaction shape note above runs: `wave-converged` if every declared `node_id` now has a `TERMINAL`-and-merged lineage-head, then `run.completed` if the DAG's every `node_id` does.

`gauntlet-wave-declare` (FASE-003, this phase's only cross-command edit) gains the identical scope pre-pass as a declare-time rejection (`WAVE-SCOPE-OVERLAP`) — the primary defense; `gauntlet-converge`'s own pre-pass becomes genuinely unreachable through the public CLI once this ships (a wave can't be declared with overlapping `files` in the first place), and its test coverage is direct Store injection, the same technique FASE-003's own F3/F4 regression tests (`tests/validate_orchestrator_store_contract.py`) already use to prove an inner layer also rejects a state the public layer would never produce.

### Ship gate and run abandonment (FR-006–FR-009, FR-014)

`checkpoint --step ship --state complete` (`grill_workspace.py`, unchanged entry point) gains one new check, inserted after the existing step-sequence gate (which already implies `verify`/`review` complete) and before the attestation gate. `checkpoint_command` already has a Store dependency for that attestation gate (`verify_checkpoint_attestation` calls `store.project_identity(root)`) — what it lacks is a multi-run view: the only existing projection (`run_projection`, `gauntlet_runs.py`) returns exactly one run — the "run most recent by `run_id`" selection this phase already rejected as unsound for exactly this purpose (Research Decisions). `gauntlet_runs.py` gains a new, small enumerator, `list_run_states(root, work_id) -> list[{run_id, state}]`. `_read_runs`'s own `absent_ok` only covers `work_items[work_id]` being missing from an *existing* snapshot — `store.read_snapshot(root)` itself, underneath, still fails hard (`required=True`) if the Store was never initialized for this project at all, which `_read_runs` alone does not guard against. `list_run_states` replicates `run_projection`'s actual two-layer handling instead of `_read_runs`'s single layer: it checks `store.store_exists(root)` first (the lstat-based public predicate `gauntlet_status_command` already uses — not `Path.exists()`, which follows symlinks and returns `False` for a dangling one, the wrong failure mode for a fail-closed check) and returns an empty list immediately if not — this is the case FR-008's no-op (and V2/no-Store work items) must not trip on — then calls `_read_runs(..., absent_ok=True)` only once that file is known to exist, and returns every admitted run's `run_id`/`state`, nothing else. `checkpoint_command` calls it, translating any `store.StoreError` it still raises past that point to a named block the same way every other Store-touching branch of `checkpoint_command` already does; if any entry's `state` is outside `{COMPLETE, BLOCKED}`, blocks `CONVERGENCE-INCOMPLETE` naming it. This scan explicitly does **not** go through FR-012's admission boundary — it reads Store state for the work item, it doesn't mutate anything the boundary protects.

`gauntlet-run-abandon` is the fail-closed escape hatch FR-006 already promises without naming: a run whose lineage-head worker(s) permanently failed (remediation budget spent, FASE-003) never reaches `COMPLETE`, so it would otherwise hold `ship` hostage for the rest of the work item's life. Its CLI handler still resolves `project_root`/`resolve_gauntlet_subject` the way every gauntlet handler does (root and work-item existence are not identity — this command skips only the activation-proof/`base_commit`-matching half of `gauntlet_run_admission`, not path resolution). It loads the `--attestation <path>` bundle with the same loader `checkpoint` already uses (`load_checkpoint_attestation`, `grill_workspace.py`) — any `CliFailure` that loader raises, for any reason (a missing file surfaces as `EVIDENCE-MISSING` through the same `safe_read_regular_fd` path every evidence read already uses, not just the loader's own `SYMLINK-REJECTED`/`UNSAFE-FILE`/`EVIDENCE-NOT-REGULAR` cases), is caught and translated to `ABANDON-AUTHORIZATION-INVALID` — a missing, unreadable, or malformed bundle is not a different error class from a schema failure, all of them mean "no valid authorization." A bundle that loads cleanly is then passed to `attestation._validate_human_authorization(bundle, run_id)` directly and standalone — not through `judge_checkpoint_attestation`, which needs a full resolution/dispatch/invocation chain this command has none of — and any `AttestationError` it raises (`HUMAN_AUTHORIZATION_INVALID`, `_SCOPE`, `_NOT_APPROVED`) collapses to the same single public code, the same collapse-to-one-code pattern `translate_v3_code` already applies elsewhere in this file. Only a validated bundle is passed into `gauntlet_runs.abandon_run(...)`, which records it verbatim (extension #3) and flips `state` to `BLOCKED` in the same transaction — permanently outside FR-007's scan, permanently out of `ADMITTED`/`RECOVERY_ELIGIBLE`/`RECOVERY_RECORDED`. `gauntlet_runs.py` itself gains no new dependency on `attestation` — both the loader and the validation call stay at the CLI layer, matching today's architecture where `gauntlet_runs.py` imports only `store`.

### Status projection (FR-011)

`gauntlet-status`'s existing `run_projection` (`gauntlet_runs.py`) gains a `waves` list — `wave_id`/`state`/`converged_count`/`member_count` per real (non-placeholder) wave, iterated in declaration order — and, per FR-011's own wording ("the most recent wave record that has one," not "the current wave"), the `last_conflict` of the **last wave in that iteration, scanned in reverse, whose `last_conflict` is present** — not assumed to be the newest wave overall, since the exact scenario extension #4's guard exception exists for is a newer wave already declared while an older one's conflict is still open. Both are direct field reads off the Store snapshot already in hand; no new Store call, no journal scan, no receipt probing.

### Phase boundary and compatibility

FASE-004 owns convergence, the run's terminal lifecycle, the ship-completeness gate, and voluntary run abandonment. It does not own: subagent invocation (unchanged, session-level), DAG generation (`tasks`, unchanged), wave/worker declaration mechanics beyond the two additions above (FASE-003, unchanged), or any push/release action (ADR-0002, unchanged — FR-009 makes this explicit). A work item with no gauntlet run at all, or only `COMPLETE`/`BLOCKED` ones, is unaffected by any new gate — V2 items included.

## Complexity Tracking

| Decision | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| One `required`/`optional` migration on the run record's key-set check, admitting two new optional write-once keys (`dag_content_sha256`, `abandon_authorization`), each with its own independent write-once guard | Both facts must be durable and tamper-evident, and neither fits any existing closed schema without changing it — `admission` is immutable and identity-bearing (can't take a new field after `run_id` is derived from it), and a bare hash (the receipt's `output_sha256`) can't recover `authorized_by` after the fact. | A single generic "run metadata" free-form field for both — rejected: mixes a load-bearing correctness input (the DAG pin, checked on every converge/declare call) with an audit record (the abandon bundle, read rarely) under one loosely-typed key, losing the write-once guard's specificity for each. |
| A narrow, named exception to the Store's newest-wave-only mutation guard, rather than a general "waves are mutable" relaxation | `last_conflict` must be writable/removable on a wave that a newer wave has since superseded (the edge case where wave N+1 is legitimately declared while wave N's conflict is still open) — the existing guard was total, with no field-level granularity. | Making the whole superseded-wave record mutable again — would undo the immutability guarantee FASE-003 built for `state`/`node_ids` of a superseded wave, a bigger and unrelated regression. |
| `expect_placeholder`'s existing `newest_state == "DECLARED"` check must be extended with `node_ids == WAVE_PENDING_NODE_IDS`, not reused as-is | Without the second condition, a wave record injected directly into the Store (bypassing the public CLI) with `state: DECLARED` and real `node_ids` — already produced by this repo's own test fixtures — would be misidentified as "the first wave," pinning the wrong DAG. | Trusting the existing single-condition check — the exact test fixture already in `tests/validate_orchestrator_store_contract.py` (`DEFAULT_WAVE_NODE_IDS`) would silently defeat FR-004c's guarantee if this weren't tightened. |
| `gauntlet-converge` implements its own run-terminal check instead of reusing the shared `_run_for_worker` guard every other coordinator command already calls | `_run_for_worker` rejects `BLOCKED`/`COMPLETE` runs uniformly — correct for every other command, but FR-005 requires one narrow exception (replaying the exact wave that completed the run must succeed, not `RUN-NOT-ELIGIBLE`) that no shared helper expresses. | Adding a bypass flag to `_run_for_worker` itself — would let every future caller opt out of the terminal-run guard, diluting a check five other commands depend on staying strict, to serve one command's one exception. |
| `checkpoint_command` gains a new small enumerator (`list_run_states`) instead of reusing `run_projection` | `run_projection` returns exactly one run — by design, for `gauntlet-status`'s single-run display — and this phase already rejected "pick one run" as the fail-open FR-007 exists to close; the ship gate needs every admitted run's state, not a display projection of one. | Extending `run_projection` itself to optionally return all runs — conflates two different callers' needs (a human-readable single-run status vs. an exhaustive gate scan) in one function, and risks the display path accidentally picking up gate semantics or vice versa. |
