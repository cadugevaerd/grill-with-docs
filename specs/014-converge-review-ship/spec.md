**Work item**: feature-gauntlet-loop-0447622ec0714933a4e791d0b58b5420 · **ADRs**: ADR-0002, ADR-0008, ADR-0009, ADR-0011, ADR-0020, ADR-0021, ADR-0022 · **DU**: DU-004

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Integrar em série apenas mudanças limpas de cada wave concluída (Priority: P1)

Depois que todos os nós de uma wave do Execution DAG chegam a um estado terminal, o coordenador integra o branch de cada worker que terminou com sucesso (commits sobre o `base_commit` da run, no seu próprio worktree) de volta ao `execution_branch` já vinculado ao work item (o mesmo campo que `EXECUTION-BRANCH-MISMATCH` já lê e compara desde FASE-001 — nenhum campo novo no Store da run). A integração roda wave por wave, na ordem em que as waves foram declaradas, nunca convergindo a wave N+1 antes da wave N estar totalmente convergida; dentro de uma wave, todos os membros passam primeiro por uma checagem de sobreposição de escopo antes de qualquer merge Git ser tentado.

**Why this priority**: É o gap que bloqueia tudo mais nesta fase — sem convergência real, o resultado de FASE-003 (workers em worktrees isolados) nunca chega a um estado único revisável, e `converged` já existe como campo morto no Store (`_workspace_identity`, sempre `False`) esperando por este dono.

**Independent Test**: Dado um worker terminal com sucesso cujo `files` declarado no Execution DAG (fonte de verdade pra sobreposição de escopo — ver ADR-0021; `grant.scope_paths` não é usado aqui porque não é garantido idêntico ao `files` do nó) não sobrepõe nenhum outro membro da mesma wave, quando o coordenador converge essa wave, o `execution_branch` passa a conter os commits desse worker e o campo `converged` do worker vira `True`.

**Acceptance Scenarios**:

1. **Given** uma wave com dois workers terminais com sucesso cujos nós têm `files` declarado no DAG que não se sobrepõe entre si, **When** o coordenador converge a wave, **Then** ambos são integrados em série (ordem alfabética de `node_id`) no `execution_branch`, cada um com seu próprio commit de integração, e ambos ficam `converged: true`.
2. **Given** uma wave com dois workers terminais com sucesso cujos nós têm `files` declarado no DAG que se sobrepõe entre si (caso que já deveria ter sido rejeitado na declaração da wave por FR-004b — este cenário cobre só o residual genuinamente inalcançável pela CLI pública, exercido por injeção direta no Store, ver justificativa de FR-002), **When** o coordenador converge a wave, **Then** a checagem de sobreposição roda como um pré-passe sobre a wave inteira, antes de qualquer merge Git; a integração bloqueia `INTEGRATION_CONFLICT` nomeando os dois `node_id` envolvidos, e **nenhum** membro da wave — nem os dois em conflito, nem qualquer outro sem sobreposição — é marcado `converged` nessa tentativa.
3. **Given** uma wave cujos membros passam no pré-passe de escopo (FR-002), mas cujo merge Git real de um deles contra o `execution_branch` (que já pode conter commits integrados de waves anteriores, ou de membros já mergeados mais cedo na mesma wave) produz conflito de conteúdo, **When** o coordenador converge, **Then** a integração bloqueia `INTEGRATION_CONFLICT` citando o worker cujo merge falhou, o `execution_branch` volta a ficar bit-a-bit idêntico ao seu estado imediatamente anterior à tentativa desse worker específico (sem merge parcial dele) — membros da mesma wave já mergeados com sucesso antes dele permanecem integrados, não são revertidos — e nenhum worker adicional dessa wave é processado até resolução manual.
4. **Given** uma wave já totalmente convergida sem conflito, **When** o coordenador reprocessa a mesma wave (retomada), **Then** a operação é idempotente — nenhum commit de integração duplicado é criado e o verdict é de reuso, não uma nova tentativa de merge.
5. **Given** a wave N ainda não está totalmente convergida, **When** o coordenador tenta convergir a wave N+1, **Then** o comando bloqueia `WAVE-CONVERGENCE-OUT-OF-ORDER` sem tocar em nenhum branch — convergência segue a mesma disciplina serial que `gauntlet-wave-declare` já aplica à criação de waves (FASE-003).
6. **Given** um worker cujo nó tem `parallel:false` (execução solo, ver FASE-003 FR-004), **When** o coordenador converge sua wave de um único membro, **Then** a integração roda pela mesma trilha serial, sem tratamento especial — uma wave de um membro não é caso distinto de uma wave de cinco.

### User Story 2 - Revisão independente antes do gate humano de ship (Priority: P1)

A macroetapa `review` é despachada ao seu próprio subagente líder — como qualquer uma das onze macroetapas (FASE-003, ADR-0016/0017) — depois que `converge` e `verify` estão ambos `complete`. Esse líder confronta especificação, plano, DAG, diffs integrados e receipts, e sua reprovação produz um bloqueio nomeado que impede `ship` de avançar, sem qualquer ciclo automático de reparo.

**Why this priority**: É o gate constitucional entre "o código passou nos testes" e "um agente confia o suficiente pra pedir autorização humana de ship" — sem ele, `ship` fica dependendo só do juízo de quem implementou.

**Independent Test**: Dado um run cujo `review` acabou de ser dispatchado, quando o checkpoint desse passo grava `blocked` em vez de `complete`, a checagem de sequência já existente desde FASE-001 (`checkpoint_command`, `any(steps.get(s) != "complete" for s in sequence[:index])`) impede que `checkpoint --step ship` seja sequer aceito pra esse work item — sem mudança de comportamento nesta fase.

**Acceptance Scenarios**:

1. **Given** um run com `converge` e `verify` ambos `complete`, **When** o coordenador despacha `review`, **Then** exatamente um subagente líder é criado para essa macroetapa, na tier `large` (piso mais alto do sistema de tiers), como qualquer outra macroetapa da sequência fixa.
2. **Given** o líder de `review` grava seu checkpoint como `blocked`, **When** o coordenador tenta avançar o run, **Then** `ship` nunca é alcançável (mecanismo genérico já existente, sem mudança), e nenhum reparo automático é acionado.
3. **Given** o líder de `review` grava seu checkpoint como `complete` e o líder de `ship` já rodou até o fim, **When** o coordenador grava `checkpoint --step ship --state complete`, **Then** essa transição só é aceita se, além de `verify`/`review` completos, nenhuma run gauntlet admitida deste work item tiver worker terminal pendente de convergência (User Story 3, FR-007) — `ship` nunca fecha sobre um resultado parcialmente integrado, mesmo que o líder de `ship` já tenha rodado inteiro achando que estava tudo pronto.

### User Story 3 - Ship nunca despacha sobre convergência incompleta (Priority: P2)

`checkpoint --step ship --state complete` passa a exigir também que toda run gauntlet V3 admitida deste work item esteja em estado terminal (`COMPLETE` ou `BLOCKED`, ADR-0020) — nunca varrendo worker por worker: `run.state == COMPLETE` já significa, por construção de FR-001, que todo `node_id` do DAG tem lineage-head `converged: true`; uma run ainda `ADMITTED`/`RECOVERY_ELIGIBLE`/`RECOVERY_RECORDED` bloqueia `ship`, seja porque tem convergência pendente, seja porque parte do DAG nem chegou a ter wave declarada — o predicado do `state` cobre os dois casos sem precisar distingui-los.

**Why this priority**: Fecha o elo que faltava entre o Store durável de runs/waves/workers (FASE-002/003) e o checkpoint genérico dos 11 passos (FASE-001): hoje um nó `FAILED`/`STALLED` com orçamento de remediação já gasto (FASE-003 FR-008/FR-009) pode deixar sua wave `COMPLETE` (`_wave_would_complete` trata qualquer estado terminal como suficiente) sem que a run inteira jamais alcance `COMPLETE`, e nada impede `ship` de prosseguir sobre esse resultado incompleto.

**Independent Test**: Dado um work item com uma run gauntlet cujo `state` ainda não é `COMPLETE` nem `BLOCKED`, quando o coordenador tenta `checkpoint --step ship --state complete`, o comando bloqueia com um código nomeado (`CONVERGENCE-INCOMPLETE`) antes do gate de attestation.

**Acceptance Scenarios**:

1. **Given** toda run gauntlet admitida do work item está `COMPLETE` ou `BLOCKED`, **When** o checkpoint de `ship` é solicitado com `verify`/`review` completos, **Then** o gate de convergência passa silenciosamente (sem novo verdict) e o fluxo segue para o gate de attestation já existente.
2. **Given** pelo menos uma run gauntlet admitida ainda não é `COMPLETE` nem `BLOCKED` (convergência pendente, `INTEGRATION_CONFLICT` sem resolução, DAG parcialmente despachado, ou lineage permanentemente `FAILED`/`STALLED` com orçamento de remediação esgotado), **When** o checkpoint de `ship` é solicitado, **Then** o comando bloqueia `CONVERGENCE-INCOMPLETE` citando a run pendente, antes de qualquer verificação de attestation.
3. **Given** um work item sem nenhuma run gauntlet V3 admitida (ou só com runs já `COMPLETE`/`BLOCKED`), **When** o checkpoint de `ship` é solicitado, **Then** o gate de convergência é um no-op e a fronteira de admissão de FR-012 não se aplica (ela é só de `gauntlet-converge`) — esta fase não torna obrigatório ter uma run gauntlet para usar o ciclo de 11 macroetapas, nem pra item V2.
4. **Given** um work item com mais de uma run gauntlet admitida, sendo que a run mais **antiga** por `run_id` já está `COMPLETE` mas uma run mais **nova** (admitida depois de um `phase-turn`, por exemplo) ainda não é `COMPLETE`/`BLOCKED`, **When** o checkpoint de `ship` é solicitado, **Then** o gate bloqueia `CONVERGENCE-INCOMPLETE` citando a run pendente — o gate varre todas as runs admitidas, nunca confia em qualquer seleção de "run única" (`run_id` não é cronológico, é um hash de admissão).
5. **Given** uma run com worker `FAILED` permanente (orçamento de remediação esgotado) que travaria `ship` para sempre, **When** um humano roda `gauntlet-run-abandon --run-id <id>` com um bundle `human-authorization/v1` válido (FR-014), **Then** essa run transiciona pra `BLOCKED`, sai do escopo do gate de FR-007, e `ship` volta a ser alcançável se toda run restante estiver `COMPLETE`/`BLOCKED` — sem isso, FR-006 (nenhuma resolução automática) deixaria o work item travado permanentemente (ADR-0020).
6. **Given** um bundle de autorização ausente ou com `decision` diferente de `APPROVED`, **When** `gauntlet-run-abandon` é chamado, **Then** o comando bloqueia `ABANDON-AUTHORIZATION-INVALID` e a run permanece no estado anterior — texto livre nunca é aceito como substituto.

### User Story 4 - Observabilidade compacta de wave e bloqueio via `gauntlet-status` (Priority: P3)

`gauntlet-status` passa a expor, além do que já retorna hoje (run/workers/`recovery_count`), um resumo compacto de waves (`wave_id`, `state`, contagem de membros convergidos) e o bloqueio de convergência mais recente ainda não resolvido, sem expor `events.jsonl` bruto nem o raciocínio de workers.

**Why this priority**: O ROADMAP promete "Run Status Events" como parte do escopo. Status de macroetapa já é visível via `development.steps`/`current_step` (FASE-001) e status de recovery já é visível via `recovery_count` (FASE-002) — o que falta é só wave e bloqueio; esta fase completa exatamente essa lacuna, sem reinventar o que já existe.

**Independent Test**: Dado um run com duas waves, uma totalmente convergida e outra ainda em andamento, `gauntlet-status --run-id <id>` retorna as duas entradas de wave com seus estados corretos, sem exigir acesso direto ao arquivo do Store.

**Acceptance Scenarios**:

1. **Given** um run com waves em estados distintos, **When** `gauntlet-status` é chamado, **Then** a projeção inclui uma lista `waves` com `wave_id`, `state` e `converged_count`/`member_count`, mantendo os campos já existentes (`workers[]`, cada um já com `failure_class`, e `recovery_count`) inalterados.
2. **Given** uma run com um bloqueio `INTEGRATION_CONFLICT` aberto, **When** `gauntlet-status` é chamado, **Then** a projeção inclui esse bloqueio (nós envolvidos, motivo) até que uma convergência subsequente bem-sucedida o resolva.

### Edge Cases

- Dois workers terminais da mesma wave, ambos `FAILED`: nenhum pode ficar `converged` (convergência só integra sucesso) — a wave nunca atinge 100% convergida até um substituto remediado (FASE-003) chegar `TERMINAL` com sucesso; se o orçamento de remediação já foi gasto (FASE-003 FR-008/FR-009), a wave fica permanentemente sem 100% de convergência e `ship` permanece bloqueado `CONVERGENCE-INCOMPLETE` — não há segunda tentativa fora do orçamento já definido pela FASE-003.
- Um worker remediado (`<node_id>-r1`, FASE-003) chega a `TERMINAL` com sucesso: a convergência integra o branch do substituto, nunca do worker original substituído. O worker original nasceu do mesmo `base_commit` que o substituto (não é um branch que o substituto continua) — qualquer commit real que o original já tivesse feito antes de ser marcado `STALLED`/`FAILED` é descartado, não migrado; isso já é um comportamento herdado da FASE-003 (remediação não é continuação de trabalho), esta fase só documenta a consequência para convergência. O worktree/branch do worker original permanece órfão indefinidamente — `cleanup_worker` (FASE-002) só age sobre `TERMINAL`/`CLEANING`, e um worker `STALLED`/`FAILED` nunca chega lá; isso é debt herdado, não algo que esta fase resolve (ver Assumptions).
- Merge de um worker cujo branch está vazio (nenhum commit além do `base_commit` — subagente não fez nenhuma mudança real): tratado como integração trivial bem-sucedida (`converged: true`, sem commit de integração novo), não como erro nem como `INTEGRATION_CONFLICT`.
- Reentrada de convergência depois de um `INTEGRATION_CONFLICT` de `reason: "content-conflict"` (FR-003) já registrado: comparado contra os fingerprints já gravados em `last_conflict` (`execution_branch_head`/`worker_heads`) — se idênticos, bloqueia de novo sem tentar recalcular um merge que já se sabe que falha; se algum head mudou desde então (ex.: um novo commit no worker), a tentativa é recalculada do zero, porque o conflito anterior já não descreve o estado atual. Reentrada depois de um `reason: "scope-overlap"` (FR-002) nunca recalcula — o `files` que causou o bloqueio já está pinado (FR-004c) e não muda, então esse caso é sempre um bloqueio incondicional, os fingerprints ali só existem por uniformidade de schema.
- Run cujo `execution_branch` foi trocado por um `phase-turn` entre a wave ter sido declarada e a convergência ser tentada: bloqueia fail-closed (`EXECUTION-BRANCH-MISMATCH`, mecanismo já existente desde FASE-001) — convergência nunca escreve num branch diferente do vinculado ao work item.
- Run cujo `execution_branch` foi **zerado** (não trocado) por um `phase-turn` entre a wave ter sido declarada e a convergência ser tentada: a checagem genérica de `checkpoint`/`phase_turn_command` trata `execution_branch: null` como backfill legítimo e deixaria passar — mas `gauntlet-converge` (diferente do checkpoint genérico, que só grava metadado) está prestes a escrever commits reais, então FR-001 exige explicitamente que `development.execution_branch` não seja nulo antes de qualquer merge, bloqueando `EXECUTION-BRANCH-UNSET` em vez de silenciosamente adotar o branch atual como se fosse a primeira vez.
- Convergir a wave N+1 antes da wave N estar 100% convergida (ex.: um bloqueio `INTEGRATION_CONFLICT` da wave N ainda aberto): bloqueia `WAVE-CONVERGENCE-OUT-OF-ORDER`, mesmo que os `node_id` da wave N+1 não tenham nenhuma sobreposição de escopo com nada pendente — a ordem é por wave, não por escopo.
- A árvore de trabalho principal (onde `execution_branch` está checked out) está suja no momento da convergência (mudanças locais não commitadas, fora do controle de qualquer worker): bloqueia fail-closed (`EXECUTION-TREE-DIRTY`, FR-001), nunca classificado como `INTEGRATION_CONFLICT` — esse código é especificamente sobre conteúdo divergente entre workers, não sobre o estado local de quem roda o comando.
- Um worker `FAILED`/`STALLED` de uma run antiga tem orçamento de remediação esgotado e nunca vai convergir: um humano roda `gauntlet-run-abandon` (FR-014, ADR-0020) pra marcar essa run `BLOCKED`; a partir daí o gate de `ship` (FR-007) para de contar essa run — sem isso, o work item ficaria travado pra sempre (ver ADR-0020).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: O sistema DEVE prover um comando `gauntlet-converge` que, depois da fronteira de admissão comum (FR-012) e antes de qualquer lógica específica de convergência, bloqueia `DAG-PIN-MISSING` se a run não tem o hash do DAG pinado (FR-004c) — nunca converge sobre um `--dag` não vinculado à run. Passado esse gate, integra, wave por wave (na ordem de declaração) e, dentro de uma wave, na ordem alfabética de `node_id`, o branch de cada worker terminal com sucesso de volta ao `execution_branch` do work item, exigindo `development.execution_branch` não-nulo e a árvore de trabalho principal limpa antes de qualquer merge (bloqueando `EXECUTION-BRANCH-UNSET` ou `EXECUTION-TREE-DIRTY`, respectivamente, nunca classificados como `INTEGRATION_CONFLICT`), marcando cada worker integrado com sucesso como `converged: true`. Quando, depois de uma convergência bem-sucedida, **todo `node_id` do Execution DAG** (`--dag`, o mesmo argumento que o comando já recebe) tem um worker de lineage-head `converged: true` — não "nenhuma wave pendente no Store", condição que fecharia a run assim que a primeira wave convergesse, antes da segunda sequer existir — a run transiciona `state` para `COMPLETE` (ADR-0020). Essa transição exige estender `store.py`'s `run_edges` com `ADMITTED→COMPLETE` e `RECOVERY_ELIGIBLE→COMPLETE` (hoje só `RECOVERY_RECORDED→COMPLETE` existe) — extensão de schema explícita desta fase, não comportamento já existente.
- **FR-002**: Antes de tentar qualquer merge Git para uma wave, o sistema DEVE checar, em um único pré-passe sobre todos os membros dessa wave, sobreposição entre o `files` declarado no Execution DAG (`--dag`, revalidado inline, mesmo padrão que `gauntlet-wave-declare` já usa — não `grant.scope_paths`, que não é garantido idêntico ao `files` do nó, ver ADR-0021) de cada par de membros; qualquer sobreposição bloqueia `INTEGRATION_CONFLICT` para a wave inteira antes de qualquer merge, gravando `last_conflict: {node_ids: [...], reason: "scope-overlap", execution_branch_head: <sha>, worker_heads: {...}}` no registro da wave — mesmo schema fechado de 4 chaves que FR-003 usa (ver adiante), sempre as mesmas quatro em ambos os casos, nunca um subconjunto condicional (todo `node_id` sobreposto, sem limite de contagem; `store.py`'s guard de wave-mais-nova ganha exceção estreita pra permitir escrever/remover só este campo numa wave superada — ver ADR-0022) — nenhum membro da wave é marcado `converged` nessa tentativa, mesmo os que não sobrepõem nada. Como `files` já está pinado pela geração corrente do DAG (FR-004c), um `scope-overlap` é determinístico: reentrada nunca recalcula, bloqueia de novo incondicionalmente, os fingerprints existem só por uniformidade de schema e depuração, não porque a decisão dependa deles. Com FR-004c corrigido (pin no lugar certo do ciclo de vida da wave), este caminho é defesa em profundidade genuinamente inalcançável pela CLI pública — toda wave real só existe depois de passar por FR-004b, que já rejeitaria a mesma sobreposição antes. A cobertura de teste é por injeção direta no Store, mesmo padrão que a FASE-003 já usa nos próprios testes de regressão F3/F4 (`tests/validate_orchestrator_store_contract.py`, `test_store_rejects_two_new_remediation_records_for_the_same_node_in_one_transaction` e `test_wave_out_of_order_id_injection_is_rejected`) pra provar que uma camada interna também recusa um estado que a camada pública nunca deixaria existir — não é teste morto, é a mesma disciplina de defesa em profundidade que este repositório já pratica.
- **FR-003**: Quando o pré-passe de escopo (FR-002) passa mas o merge Git real de um worker contra o `execution_branch` (que pode já conter integrações de waves anteriores, ou de membros já mergeados mais cedo na mesma wave) produz conflito de conteúdo, o sistema DEVE bloquear `INTEGRATION_CONFLICT`, gravando `last_conflict: {node_ids: [<node_id do worker>], reason: "content-conflict", execution_branch_head: <sha do execution_branch antes da tentativa>, worker_heads: {<node_id do worker>: <sha do branch do worker>}}` no registro da wave — diferente de `scope-overlap`, aqui os fingerprints são a própria decisão de reentrada: se `execution_branch_head` e o `worker_heads` daquele nó ainda batem com o registrado, bloqueia de novo sem recalcular; se qualquer um mudou (novo commit no worker, ou a wave anterior mudou o `execution_branch`), a tentativa é refeita do zero — sem deixar merge parcial no `execution_branch` (a tentativa falha desse worker é revertida atomicamente antes do comando retornar; membros já integrados com sucesso antes dele na mesma chamada permanecem), e sem processar o restante da wave até resolução manual.
- **FR-004**: `gauntlet-converge` DEVE bloquear `WAVE-CONVERGENCE-OUT-OF-ORDER` se a wave solicitada não for a próxima wave ainda não totalmente convergida da run, na ordem de declaração — nenhuma wave é convergida antes da anterior estar 100% `converged`.
- **FR-004b**: `gauntlet-wave-declare` (FASE-003) DEVE, nesta fase, aplicar a mesma checagem de sobreposição de `files` da FR-002 já na declaração da wave — antes de qualquer worker ser preparado — bloqueando `WAVE-SCOPE-OVERLAP` e nomeando os `node_id` sobrepostos. Uma sobreposição de `files` entre dois nós que o DAG já declara mutuamente independentes (`parallel:true`, sem aresta de dependência entre si) é, por definição, um defeito de planejamento upstream (`tasks`/`agent-assign`) — rejeitar cedo, antes de gastar dispatch de worker, é estritamente melhor que descobrir em FR-002 depois do trabalho feito (ver Assumptions sobre a tensão com paralelismo).
- **FR-004c**: `gauntlet-wave-declare` DEVE pinar o hash do conteúdo do `--dag` fornecido (`store.jcs_sha256` do documento já parseado — a mesma primitiva de digest que `gauntlet_runs.py` já usa pra admission/receipt/evento; `gauntlet-dag-validate` hoje não calcula nem retorna esse valor, então esta fase adiciona esse cálculo ao caminho de carregamento do DAG, não reusa algo que já existia) exatamente quando substitui o placeholder que toda admissão já cria (`waves: {wave-0001: {state: DECLARED, node_ids: WAVE_PENDING_NODE_IDS}}`, FASE-002/003 — nenhuma run, de nenhuma geração, jamais tem `run["waves"]` vazio, então "primeira chamada de sempre" não pode significar isso). O predicado reforça o `expect_placeholder` que `declare_wave` já calcula (`newest_state == "DECLARED"`) com a checagem de `node_ids == WAVE_PENDING_NODE_IDS` que o código hoje **não** faz — sem esse reforço, um estado de wave injetado diretamente no Store (fora da CLI pública) com `state: DECLARED` e `node_ids` reais, como os próprios fixtures de teste já produzem, seria tratado como "primeira wave" e pinaria incorretamente. Pela CLI pública isso é inequívoco de qualquer forma: só `wave-0001` no seu estado inicial nasce `DECLARED`+`WAVE_PENDING_NODE_IDS`; toda wave seguinte já nasce `ACTIVE`. Uma run que já tem qualquer wave **real** (não-placeholder) registrada e ainda não tem pin — inclusive uma run legada, criada antes de FR-004c existir — bloqueia `DAG-PIN-MISSING` em **toda** chamada seguinte de `gauntlet-wave-declare`, do mesmo jeito que já bloqueia em `gauntlet-converge` (FR-001) — nunca adota o `--dag` de uma wave posterior como se fosse a primeira, porque esse `--dag` pode não cobrir mais `node_id` que waves anteriores já trataram como existentes (ex.: `tasks.md` regenerado depois que uma wave já rodou, um nó que sumiu do novo DAG nunca seria contado por FR-001, e a run fecharia `COMPLETE` sobre um DAG truncado sem ele). A única saída pra uma run legada sem pin é `gauntlet-run-abandon` (FR-014) — nunca uma declaração tardia que sintetiza retroativamente "isso é a primeira wave". O campo é **novo, opcional, write-once** (nunca removível — não existe caminho presente→ausente) — precisa de duas extensões nomeadas no Store, no mesmo espírito das duas que ADR-0022 já precisou pra `last_conflict`: (a) o conjunto fechado de chaves da run em `store.py` (hoje `{admission, state, recovery_count, waves, workers, last_transition}`) ganha esta chave como **opcional** — não pelo helper `_closed_object` (igualdade estrita de conjunto, sem noção de opcional), mas pelo padrão `required`/`optional` que `_transition_fields` já usa pro envelope de evento (`store.py`); (b) um guard write-once na validação de transição (mesmo lugar que já protege `admission` inteiro), que aceita ausente→presente uma vez e rejeita qualquer escrita seguinte, divergente ou não. Toda chamada seguinte de `gauntlet-wave-declare` ou `gauntlet-converge` para essa run DEVE revalidar seu próprio `--dag` contra o hash já pinado, bloqueando `DAG-CONTENT-MISMATCH` se divergir. Sem isso, a condição de fechamento de FR-001 ("todo `node_id` do DAG converged") calcularia sobre um DAG diferente do que as waves foram declaradas — e `COMPLETE` é uma transição absorvente (ADR-0020): fechar a run cedo demais sobre um `--dag` truncado não tem volta.
- **FR-005**: `gauntlet-converge` DEVE ser idempotente: reprocessar uma wave já totalmente convergida retorna um verdict de reuso sem criar novo commit de integração nem repetir uma tentativa de merge já conhecida como conflitante — mesmo quando essa foi a wave que completou a run (run já `COMPLETE`, FR-001): reprocessar a **mesma** wave que já convergiu continua retornando reuso; o guard de run terminal (que rejeita `RUN-NOT-ELIGIBLE` outras mutações contra uma run `COMPLETE`/`BLOCKED`) só se aplica a pedir convergência de uma wave **diferente** ou nova depois do fechamento — nunca ao replay idêntico da última wave.
- **FR-006**: O sistema NÃO DEVE prover nenhuma resolução automática de `INTEGRATION_CONFLICT` (sem auto-merge, sem reescrita do DAG, sem retry silencioso) — resolução é sempre um ato humano (que pode incluir `gauntlet-run-abandon`, FR-014, quando a run inteira se torna irrecuperável) ou de nova especificação, fora do escopo desta run.
- **FR-007**: `checkpoint --step ship --state complete` DEVE bloquear `CONVERGENCE-INCOMPLETE`, citando a(s) run(s) pendente(s), antes do gate de attestation, se existir qualquer run gauntlet V3 admitida para este work item cujo `state` **não** é `COMPLETE` e **não** é `BLOCKED`. O predicado é só o `state` da run (ADR-0020 já garante que `COMPLETE` só é alcançado quando todo `node_id` do DAG tem lineage-head `converged: true`) — não uma varredura própria de workers/waves, que seria vaziamente satisfeita por um `node_id` do DAG cuja wave nunca chegou a ser declarada (uma run `ADMITTED` com um DAG só parcialmente despachado não tem worker pendente nenhum pra citar, mas também está longe de pronta). Esse gate roda depois que o líder de `ship` já foi despachado e terminou (na transição pra `complete`), no mesmo ponto em que a attestation já é checada hoje — não no despacho inicial (`--state in-progress`).
- **FR-008**: Quando o work item não tem nenhuma run gauntlet V3 não-terminal admitida, o gate de FR-007 é um no-op — `ship` segue seus gates já existentes (sequência de passos completos, attestation) sem exigir uma run gauntlet, e sem exigir a fronteira de admissão de FR-012 (que é só para `gauntlet-converge`).
- **FR-009**: Nenhum comando desta fase (`gauntlet-converge`, `gauntlet-run-abandon`, ou o gate de FR-007) executa push, force-push ou release para um remoto Git — toda ação em Git remoto continua exclusiva do fluxo humano de `ship` já existente (ADR-0002); esta fase só integra branches locais.
- **FR-010**: O sistema DEVE registrar em `events.jsonl` um evento append-only por transição relevante de convergência (`gauntlet.converge.worker-converged`, `gauntlet.converge.conflict`, `gauntlet.converge.wave-converged`, `gauntlet.run.completed`, `gauntlet.run.abandoned`), seguindo o mesmo formato de encadeamento por hash já usado pelos eventos de FASE-002/003. O evento de conflito confirma só que houve conflito e em qual wave (allowlist fechada, sem mudança) — nunca carrega `node_id` nem motivo, ver FR-011.
- **FR-011**: `gauntlet-status` DEVE expor, além dos campos já retornados hoje, uma lista `waves` (`wave_id`, `state`, `converged_count`, `member_count`) — excluindo o placeholder `wave-0001` que toda admissão cria (`node_ids == WAVE_PENDING_NODE_IDS`, um sentinel interno de bootstrap, nunca uma wave real; a mesma checagem `expect_placeholder` que FR-004c usa decide se uma entrada é sentinel ou real) — e, se houver, o campo `last_conflict` (`node_ids: [...]`, `reason`) do registro da wave mais recente que o tiver — lido diretamente do Store, não reconstruído por sondagem (ADR-0022: nem o evento nem o receipt de transição têm campo livre pra essa identidade; `last_conflict` é uma extensão de schema explícita do registro da wave, escrita por FR-002/FR-003 na mesma transação do evento de conflito, e removida na próxima convergência bem-sucedida daquela wave — sua ausência é o sinal de "resolvido"). `gauntlet-status` nunca expõe `events.jsonl` bruto nem o conteúdo de qualquer diff de worker.
- **FR-012**: `gauntlet-converge` (e só ele — não o gate de FR-007, que é sobre `ship` e roda mesmo pra item V2, ver FR-008) DEVE herdar a fronteira de admissão comum já estabelecida (`gauntlet_run_admission`): ativação FASE-001 stale ou ausente bloqueia `ACTIVATION-REQUIRED`/`IDENTITY-STALE`; item V2 bloqueia `WORKFLOW-INCOMPATIBLE`; commit base Git indisponível bloqueia `BASE-COMMIT-UNAVAILABLE` — antes de qualquer lógica específica do comando.
- **FR-013**: Toda mudança em `plugin/**` desta fase segue a regra constitucional de bump obrigatório de versão — `tests/validate_distribution.py` e `tests/check_version_bump.py --base-ref origin/main` DEVEM confirmar bump antes do ship desta fase, nos mesmos oito pontos de distribuição já travados hoje.
- **FR-014**: O sistema DEVE prover um comando coordinator-only `gauntlet-run-abandon` que transiciona `run.state` para `BLOCKED`, exigindo um bundle `human-authorization/v1` completo (recebido via `--attestation <path>`, mesma convenção de flag que `checkpoint` já usa pra receber seu próprio bundle) (as 6 chaves exatas que `attestation.py` já valida pra `ship` — `schema`, `scope`, `decision: APPROVED`, `authorized_by`, `receipt_ref`, `content_sha256`; aqui `scope` é o `run_id` alvo, não um `step_id` — `_validate_human_authorization` compara por igualdade de string pura, sem exigir que `scope` seja um passo do ciclo de 11) — nunca um `--reason` de texto livre. Isso é honestamente uma barreira **atribucional, não preventiva**: `_validate_human_authorization` valida só forma (schema, `decision == APPROVED`, formato dos campos) e a própria `attestation.py` documenta que esse bundle "is accepted but never inspected" pela cadeia que dá força real ao gate de `ship` (resolution→dispatch→invocation→step-output, cada elo correlacionado e ancorado em disco) — `gauntlet-run-abandon` não tem essa cadeia porque não é um dos 11 passos, então reusar o schema não empresta a força da attestation, só exige que alguém construa deliberadamente um documento específico em vez de aceitar texto livre, e vincula esse documento à run que ele autoriza (`scope == run_id`, um bundle nunca reaproveitado noutra run). O bundle inteiro (as 6 chaves) DEVE ficar durável, não só validado e descartado — um hash sozinho (`output_sha256` do receipt, hoje sempre `None` em toda transição gauntlet) provaria que ALGUM bundle existiu, mas não recuperaria `authorized_by`/`receipt_ref` de volta, então não serve como registro de quem autorizou. A run ganha uma **segunda** chave nova, opcional, write-once (mesmo mecanismo de FR-004c: `required`/`optional` no lugar de `_closed_object`, mais um guard de transição) — `abandon_authorization`, o bundle completo copiado verbatim no momento da transição. Diferente do pin do DAG, aqui write-once é natural, não uma escolha: `run.state` só alcança `BLOCKED` uma vez (transição absorvente), então só pode haver uma autorização de abandono por run. Mint de evento append-only (FR-010) na mesma transação; transição nunca reversível de volta para `ADMITTED`/`RECOVERY_ELIGIBLE`/`RECOVERY_RECORDED`. Bundle ausente ou inválido bloqueia `ABANDON-AUTHORIZATION-INVALID`, nomeado e testável (SC-006). Ao contrário de todo outro comando desta superfície (`gauntlet-converge` incluído, via FR-012), `gauntlet-run-abandon` NÃO exige que a `admission` da run alvo bata com a ativação/`base_commit` correntes — deriva `base_commit` e os demais campos de identidade da própria `admission` já gravada na run alvo, nunca da ativação atual, e pula a checagem de existência do commit no Git (`_require_base_commit`) sobre esse `base_commit` derivado — uma run velha o bastante pra precisar de abandono pode ter um `base_commit` que um squash/gc já tornou irrecuperável no Git, e isso não pode ser motivo de o próprio abandono falhar. Essa é a única razão de existir do desvio de identidade: destravar exatamente uma run de geração antiga, cujo `base_commit` structuralmente não bate mais com o que está ativo agora (ex.: depois de um `phase-turn` de uma fase seguinte) — se exigisse identidade corrente, seria inútil justamente no caso que motiva FR-007/ADR-0020. FR-012 (fronteira de admissão comum) não se aplica a este comando — nem pra exigi-la nem pra dispensá-la explicitamente, porque a identidade que ela checaria é exatamente a que este comando delibera não usar. É o único ato humano nomeado que remove uma run permanentemente pendente do escopo de FR-007; sem ele, um único worker sem orçamento de remediação em qualquer run passada travaria `ship` para sempre — e é também a única saída pra uma wave presa em `scope-overlap` (FR-002 — hoje só alcançável por injeção direta no Store, não pela CLI pública, já que FR-004b já rejeita o mesmo caso na declaração), já que esse bloqueio nunca se resolve sozinho (`files` pinado é imutável, ver FR-004c).

### Key Entities

- **Convergência de Worker**: o resultado de integrar o branch de um worker terminal com sucesso ao `execution_branch`; representado pelo campo `converged` já existente (até aqui sempre `False`) no registro do worker no Store, mais o commit de integração no `execution_branch` quando aplicável.
- **Bloqueio de Integração**: um `INTEGRATION_CONFLICT` nomeado, citando o(s) `node_id` envolvido(s) e o motivo (sobreposição de escopo declarada vs. conflito de conteúdo real). Não é um novo estado do Store — em particular, não reaproveita o estado `CONFLICT` já declarado (mas nunca alcançável a partir de `TERMINAL`) em `WORKER_STATES`, para não abrir uma transição nova na máquina de estados do Store. Sua identidade e motivo vivem no campo opcional `last_conflict` do registro da wave — uma extensão de schema explícita (mesmo padrão que FASE-003 já usou pra `node_ids` da wave), não reconstruída por sondagem de receipt nem carregada pelo evento (ADR-0022, ver FR-011); "aberto"/"resolvido" é simplesmente presença/ausência do campo, removido na próxima convergência bem-sucedida daquela wave.
- **Ciclo de vida terminal da run**: `run.state` alcança `COMPLETE` (convergência 100% bem-sucedida, FR-001) ou `BLOCKED` (abandono humano explícito, FR-014) — os dois únicos estados que removem uma run do escopo do gate de `ship` (FR-007). Nenhum outro código além destes dois pontos escreve esses estados (ADR-0020).
- **Bloqueio de Revisão**: reuso do mecanismo genérico já existente (`checkpoint --state blocked`) para o passo `review` — não é uma entidade nova de dados, apenas um nome (`REVIEW_BLOCKED`) para um caso já coberto.
- **Run Status Event**: não é um mecanismo novo — é a combinação de (a) os eventos append-only já descritos em FR-010, e (b) a projeção pública compacta de FR-011/User Story 4. O ROADMAP nomeia isso como entregável único; esta fase não cria um terceiro conceito para representá-lo.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% dos workers terminais com sucesso de uma wave sem sobreposição de escopo e sem conflito Git real terminam convergidos (`converged: true`) depois de uma única chamada de `gauntlet-converge` por wave, na ordem correta de waves.
- **SC-002**: 0% dos casos de sobreposição de `files` declarado no DAG dentro de uma wave resultam em qualquer tentativa de merge Git — a rejeição na declaração (FR-004b) é a linha principal de defesa; o pré-passe de FR-002 em `gauntlet-converge` é a segunda linha, e quando positivo também substitui toda tentativa de merge daquela wave.
- **SC-003**: Todo merge individual que bloqueia `INTEGRATION_CONFLICT` deixa o `execution_branch` bit-a-bit idêntico ao seu estado imediatamente anterior à tentativa desse worker específico (verificável por hash do commit HEAD antes/depois daquele merge) — membros da mesma wave já integrados com sucesso mais cedo na mesma chamada não são revertidos por um conflito posterior.
- **SC-004**: `checkpoint --step ship --state complete` nunca é aceito enquanto existir, para o work item, **qualquer** run gauntlet V3 admitida cujo `state` não seja `COMPLETE` nem `BLOCKED` — verificado por teste de contrato com duas runs admitidas, uma `COMPLETE` e outra ainda `ADMITTED` com um `node_id` do DAG sem wave declarada (não só "worker não convergido" — o caso vazio que FR-007 existe pra fechar), que tenta o checkpoint e espera bloqueio `CONVERGENCE-INCOMPLETE` antes do gate de attestation; e por um teste que confirma que uma run `BLOCKED` via `gauntlet-run-abandon` deixa de contar.
- **SC-005**: `gauntlet-status` reporta o estado de toda wave de uma run em uma única chamada, sem exigir leitura direta do Store por quem consome o comando.
- **SC-006**: A suíte de contrato desta fase usa `git` real (já é a convenção do repositório para testes de contrato — `validate_gauntlet_run_contract.py` já inicializa repositórios Git reais) e cobre, no mínimo: integração limpa multi-wave, sobreposição de escopo rejeitada na declaração da wave (FR-004b) e no pré-passe residual de converge (FR-002), `DAG-CONTENT-MISMATCH` quando o `--dag` diverge do hash pinado (FR-004c), conflito Git real entre waves, árvore suja (`EXECUTION-TREE-DIRTY`) e branch ausente (`EXECUTION-BRANCH-UNSET`), ordem de wave violada, gravação e remoção de `last_conflict` numa wave que não é mais a mais nova da run (FR-002/FR-003, ADR-0022), idempotência de reconvergência inclusive sobre a wave que fechou a run (FR-005), worker permanentemente falho bloqueando ship até `gauntlet-run-abandon` com bundle válido, `ABANDON-AUTHORIZATION-INVALID` quando o bundle está ausente ou `decision` não é `APPROVED`, `DAG-PIN-MISSING` numa run legada sem pin em `gauntlet-wave-declare` (não só em `gauntlet-converge`), run transicionando pra `COMPLETE` só quando todo `node_id` do DAG converge (FR-001), gate de ship bloqueado por uma run não-padrão entre múltiplas admitidas, gate de ship bloqueado por DAG parcialmente despachado sem worker pendente pra citar, gate de ship liberado, compatibilidade com item V2/sem run gauntlet, e adapter/runtime não comprovado — sem depender de `specify`, `node` ou `backlogctl` reais (as três ferramentas que o `CLAUDE.md` do repositório proíbe para a suíte).
- **SC-007**: O bump de versão constitucional desta fase (FR-013) é confirmado por `tests/validate_distribution.py` e `tests/check_version_bump.py` antes do ship.

## Assumptions

- **A-001**: Cada worker faz seus commits reais dentro do próprio worktree/branch (`wt-<run-id>-<worker-id>`) durante sua execução — este documento não introduz um passo de "commit" no core; o core segue nunca baixando bytes nem executando ações de negócio, só orquestrando Git localmente já disponível.
- **A-002**: ADR-0008 ("subagente grande, novo e sem escrita, distinto de quem planejou ou executou") permanece, como em FASE-003/ADR-0019, uma restrição de construção do prompt de dispatch em ambas as metades — nem "distinto de quem executou" nem "sem escrita" têm hoje uma primitiva de runtime que os verifique (o core não tem identidade de sessão/agente, e macro-passos despachados pelo mecanismo genérico de FASE-001 não passam pelo sistema de Capability Grant, que hoje só existe para workers de DAG). Esta fase não inventa nem uma primitiva de identidade nem uma extensão do sistema de grant só para simular esse enforcement; não há nenhuma checagem retroativa possível sobre dispatches já feitos.
- **A-003**: Um nó do DAG cujo `files` declarado é subconjunto vazio não pode existir — já rejeitado por FASE-003 (`DAG-MALFORMED` na origem, mesma validação que `gauntlet-dag-validate`/`gauntlet-wave-declare` já reusam); logo, toda checagem de sobreposição de escopo (FR-002, FR-004b) sempre opera sobre conjuntos não vazios. `grant.scope_paths` continua tendo sua própria garantia de não-vazio no Store (`store.py:786`), mas não é a fonte usada por essas checagens (ADR-0021).
- **A-004**: `cleanup_eligible` (o terceiro flag que `cleanup_worker` exige, ao lado de `clean` e `converged`) — nenhum código hoje o seta `True` em lugar nenhum, e esta fase não adiciona código que o faça (só dá dono a `converged`). `gauntlet-cleanup` continua incapaz de remover qualquer worktree mesmo depois de FR-001 implementada. Isso é debt explicitamente fora do escopo desta fase, não uma lacuna que esta especificação deveria fechar — dar-lhe dono é trabalho de uma fase futura.
- **A-005**: Bump de versão desta fase: a distribuição está em `2.7.0` (consumida pela FASE-003, já shipada e já publicada em `origin/main`); tanto `PLAN-CONTEXT.md` quanto `ROADMAP.md` (seção FASE-004) tinham uma nota desatualizada citando `2.6.0` — ambas corrigidas para `2.8.0` durante esta especificação, seguindo a mesma regra constitucional de bump obrigatório por mudança em `plugin/**` (FR-013).
- **A-006**: No momento desta especificação, a FASE-003 está `blocked` no ledger do work item (`BL-0003` aberto — falta de ferramenta de attestation V3 genuína, não defeito de código; FASE-003 já está shipada em `origin/main`). Esta especificação prossegue mesmo assim, seguindo o mesmo precedente já estabelecido nesta sessão para a própria FASE-003: trabalho substantivo (specify → plan → tasks → implementação → converge/verify/review por autoria direta e crítica independente) avança sem depender do `checkpoint` V3 formal, que continua indisponível pela mesma razão de ferramenta ausente — não uma exceção nova desta fase.
- **A-007**: FR-004b (ADR-0021) rejeita, na declaração da wave, qualquer sobreposição de `files` entre nós que o DAG já declara mutuamente independentes. Se `tasks`/`agent-assign` (macroetapas anteriores, fora do escopo desta fase) gerarem DAGs onde nós de fato independentes compartilham `files` com frequência — e não só nós em relação de dependência sequencial, que nunca disputam a mesma wave — essa rejeição pode se tornar o caminho comum, não a exceção, achatando o paralelismo que o DAG existe pra explorar. Esta fase aceita esse risco deliberadamente (uma sobreposição real dentro de uma wave é um defeito de planejamento, não um evento raro a tolerar) e não tenta mitigá-lo aqui; se a taxa de rejeição se mostrar alta em uso real, é evidência para revisar `tasks`/`agent-assign`, não para afrouxar FR-004b.
- **A-008**: Todo worker de toda wave nasce do `base_commit` original da run (`store.py`, `workspace["base_commit"] == run["admission"]["base_commit"]`, obrigatório pra todo worker) — nunca do `execution_branch` já atualizado por uma wave anterior convergida. Um worker da wave N+1 é cego ao código que a wave N integrou, mesmo quando `_node_ready` (FASE-003) já considera sua dependência "pronta" (terminal, não necessariamente integrada). Isso torna `content-conflict` (FR-003) o caminho **esperado** em runs com dependência real entre waves, não uma exceção rara — é o custo que FR-006 (zero resolução automática) já paga deliberadamente. `gauntlet-converge` não testa nada disso: é `verify`, a macroetapa seguinte na sequência fixa, que roda contra o `execution_branch` já integrado e é onde uma integração que mergeia limpo mas quebra semanticamente é pega — não nesta fase.
