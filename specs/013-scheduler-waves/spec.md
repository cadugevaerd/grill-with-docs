# Feature Specification: Claude Scheduler Waves

**Feature Branch**: `013-scheduler-waves`

**Created**: 2026-08-15

**Status**: Draft

**Input**: User description: "Implement FASE-003 Claude-native scheduler: dispatch each of the eleven canonical macro-steps to a Claude subagent leader in fixed order, and within agent-execute, dispatch independent Execution DAG nodes to up to five concurrent worker waves, observing progress and recovering a limited stall automatically."

**Work item**: feature-gauntlet-loop-0447622ec0714933a4e791d0b58b5420 · **ADRs**: ADR-0001, ADR-0004, ADR-0005, ADR-0007, ADR-0012, ADR-0013, ADR-0014, ADR-0015, ADR-0016, ADR-0017, ADR-0018, ADR-0019 · **DU**: DU-003

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Dispatch each macro-step to its own subagent leader, in fixed order (Priority: P1)

A coordinator dispatches each of the eleven canonical macro-steps (specify, plan, checklist, tasks, analyze, agent-assign, agent-execute, converge, verify, review, ship) to one Claude subagent leader, strictly in that order, never starting a macro-step before the previous one is terminal and never running two macro-steps concurrently.

**Why this priority**: This is the baseline capability the handoff names first ("Cada macroetapa usa um subagente Claude") and everything else in this phase happens inside one macro-step's dispatch (`agent-execute`); without fixed-order single-leader dispatch there is no scheduler to wave-parallelize inside.

**Independent Test**: Given a run ready to advance, dispatching the next macro-step creates exactly one subagent leader for that macro-step, at the tier the existing tier policy declares for it, and the following macro-step is never dispatched until the current one reaches a terminal state.

**Acceptance Scenarios**:

1. **Given** a run whose current macro-step is `checklist`, **When** the coordinator dispatches, **Then** exactly one subagent leader is created for `checklist`, invoked at the tier policy's `small` floor, and no other macro-step's leader is concurrently active.
2. **Given** a macro-step leader that has not yet reached a terminal state, **When** the coordinator evaluates the run, **Then** the next macro-step is never dispatched.
3. **Given** the `tasks` macro-step's leader completes, **When** the coordinator inspects its output, **Then** the produced Execution DAG becomes the versioned artifact this phase validates and later dispatches waves against; no separate DAG-generation step runs.
4. **Given** a macro-step leader's checkpoint records `blocked` instead of `complete`, **When** the coordinator evaluates the run, **Then** the run halts, no further macro-step is dispatched, and the coordinator takes no automatic action to resolve or bypass the block.
5. **Given** every Execution DAG node of the current `agent-execute` macro-step has reached a terminal state, **When** the `agent-execute` leader observes it, **Then** that leader submits its own checkpoint receipt as `complete` through the same attestation chain any other macro-step leader uses, and the outer dispatch loop advances to `converge` next — no dispatched worker of the wave submits that receipt, and no exception to the attestation contract is needed.

### User Story 2 - Dispatch an independent wave of workers inside agent-execute (Priority: P1)

While `agent-execute` is the current macro-step, its dispatched leader (User Story 1) dispatches a wave of Claude subagent workers to exactly the Execution DAG nodes that are both marked parallel-eligible and whose declared dependencies are already terminal, each at the tier its node declares, without exceeding the run's configured concurrent worker cap.

**Why this priority**: Parallel dispatch bounded by the declared DAG, its `parallel` flag, and the tier policy is the specific value this phase adds inside `agent-execute`; every other behavior in this story exists to keep that dispatch safe.

**Independent Test**: Given an `agent-execute` macro-step with an Execution DAG containing ready nodes, dependency-pending nodes, and a `parallel:false` node with terminal dependencies, dispatching a wave creates workers only for the ready `parallel:true` nodes plus, alone, any single ready `parallel:false` node, each at its declared tier, and never exceeds the run's configured concurrent worker cap (1-5).

**Acceptance Scenarios**:

1. **Given** an Execution DAG where two `parallel:true` nodes have no pending dependencies and three nodes depend on them, **When** the coordinator dispatches a wave, **Then** exactly the two independent `parallel:true` nodes receive workers and the three dependent nodes remain undispatched.
2. **Given** a ready node marked `parallel:false`, **When** the coordinator dispatches a wave containing it, **Then** that node is dispatched alone in its own wave, with no other node concurrently active in that same run.
3. **Given** a run configured with a worker cap of three and five independent `parallel:true` nodes ready in the same wave, **When** the coordinator dispatches, **Then** exactly three workers are created and the remaining ready nodes wait for a later wave; the cap counts concurrently active workers, so a node that finishes frees its slot for the next wave.
4. **Given** a node whose declared `tier` is `large`, **When** its worker is dispatched, **Then** it is invoked at that tier, the canonical skill and registry hash pinned at FASE-001 activation are resolved and used, and the tier decision is recorded before dispatch.
5. **Given** an Execution DAG whose declared `max_workers` exceeds the run's activation-configured worker cap, **When** the coordinator evaluates the run for dispatch, **Then** the activation-configured cap governs and the excess is never dispatched; if the DAG's declared cap is below the activation cap, the DAG's lower value governs instead.
6. **Given** more independent ready nodes than fit in one wave, **When** the first wave's workers all reach a terminal state, **Then** the coordinator declares a new, distinctly identified wave for the next eligible nodes, and the prior wave's record remains unchanged.
7. **Given** an Execution DAG containing a node whose declared `files` include a path with a `.specify/reports/` segment, **When** the coordinator evaluates the DAG for dispatch, **Then** the entire DAG is rejected as malformed before any worker is created, and no wave, worker, lease, or grant state is created for any node.
8. **Given** an Execution DAG containing a node whose declared `files` include a path under `.grill/work-items/<id>/` (for example that work item's `ROUND-LOG.jsonl` or `state.json`), **When** the coordinator evaluates the DAG for dispatch, **Then** the entire DAG is rejected exactly as in scenario 7 — the match is by the `.grill` path segment, so every file in the governance ledger is covered, not a fixed list of basenames that a new ledger file could fall outside of.

### User Story 3 - Observe worker progress and recover one stall (Priority: P2)

A coordinator observes each dispatched worker's coordinator-recorded lease transitions and, when a worker's lease shows no new transition for the run's configured stall window, replaces that worker exactly once, spending that Execution DAG node's one shared remediation budget (FR-007, ADR-0015) — independent of, and never able to trigger, FASE-002's run-level manual-resume budget; relaunching the run remains exclusively a human-operator action through FASE-002's existing manual resume, never an automatic one this phase performs. Any further failure of that node, stall or transient, after its budget is spent blocks with a diagnostic instead of remediating again.

**Why this priority**: Silent abandonment of an apparently autonomous run is the specific failure the Gauntlet Loop exists to prevent; recovery must be bounded per node, observable through evidence the coordinator already owns, and must never touch FASE-002's separate run-level manual-resume gate.

**Independent Test**: A dispatched worker's lease records no new coordinator transition for the configured stall window; the coordinator performs one remediation action against that node's own budget and records it. Simulating a further failure — stall or transient — on that same node after that remediation yields a block with a diagnostic reason, not a second automatic remediation.

**Acceptance Scenarios**:

1. **Given** a worker whose lease has recorded no new transition for the configured stall window, **When** the coordinator evaluates it, **Then** the coordinator automatically records a recovery-eligible condition against that node's own remediation budget (never FASE-002's run-level manual-resume budget), replaces that worker exactly once, and records a compact status event correlated to the run, wave, worker, and lease.
2. **Given** a node whose remediation budget has already been spent, **When** a further stall is observed on that node's current worker, **Then** the run blocks with a diagnostic reason and no further automatic recovery is attempted; relaunching the run remains available only as a separate, manual FASE-002 resume action.
3. **Given** a worker actively producing new recorded lease transitions, **When** the coordinator evaluates it before the stall window elapses, **Then** it is never classified as stalled.
4. **Given** a node whose one remediation budget was already spent — whether by an earlier stall replacement (this story) or an earlier transient retry (User Story 4) — **When** that node's current worker stalls again, **Then** the run blocks with a diagnostic reason immediately; the current worker's lease was created with the budget already spent, so no further worker is ever dispatched for that node automatically regardless of which mechanism spent the budget first.
5. **Given** a worker whose lease is approaching its original expiration but has recorded a new progress transition within the stall window, **When** the coordinator records that transition (FR-008(d)), **Then** the lease's expiration is renewed by the same fixed duration as its original grant, and the worker is never treated as expired or stalled solely because the original window elapsed.

### User Story 4 - Retry exactly one classified transient failure (Priority: P3)

A coordinator classifies a failed worker's outcome against the declared closed transient-failure classification; only a failure matching it receives exactly one automatic retry, counted against the same concurrency cap as any other active worker, and every other failure blocks for diagnosis without retrying.

**Why this priority**: Bounded, classified retry keeps the Loop autonomous for genuinely transient conditions while refusing to mask real defects behind unlimited retries or an uncapped burst of replacement workers.

**Independent Test**: A worker fails with a condition matching the declared transient classification; the coordinator retries it exactly once, without exceeding the run's worker cap. A worker fails with a non-transient condition, or fails a second time after its one retry, and the coordinator blocks instead of retrying again.

**Acceptance Scenarios**:

1. **Given** a worker failure whose recorded outcome is a process-level timeout or a transport-level dispatch failure (the declared transient set; see FR-010), **When** the coordinator observes it, **Then** exactly one automatic retry is dispatched, recorded, and counted against the run's worker cap alongside every other concurrently active worker.
2. **Given** a worker failure whose recorded outcome is a validator, gate, or contract rejection (not in the declared transient set), **When** the coordinator observes it, **Then** the run blocks with a diagnostic reason and no retry is dispatched.
3. **Given** a worker that fails a second time after its one recorded retry, **When** the coordinator observes it, **Then** the run blocks and no further retry is dispatched.
4. **Given** a node whose one remediation budget was already spent by an earlier stall replacement (User Story 3), **When** its current worker then fails with a transient-classified outcome, **Then** the run blocks with a diagnostic reason instead of dispatching a retry — the shared per-node budget (FR-007) does not reset because the second failure's mechanism differs from the first's.

### Edge Cases

- A malformed, missing, or cyclic Execution DAG must block dispatch of `agent-execute` waves before any worker is created; it must not block the `tasks` macro-step leader that produced it.
- An Execution DAG containing a node whose declared `files` match either of FR-004's two closed rejection rules (verify/review/ship evidence scope, or grill governance ledger self-attestation) must be rejected as malformed before any `agent-execute` worker is created, exactly like a cyclic DAG — never dispatched, never silently skipped.
- A wave request that would exceed the run's configured concurrent worker cap must dispatch only up to the cap and leave the remainder pending, never silently drop or silently exceed it; a stall-triggered replacement worker or a transient-failure retry counts against that same concurrent cap.
- A node whose declared `tier` is below the applicable policy floor for `agent-execute`, or that mixes Markdown and non-Markdown declared files without an explicit tier, must block that node's dispatch rather than dispatch at an unresolved tier.
- A macro-step leader must never be dispatched while a previous macro-step's leader has not yet reached a terminal state; the eleven canonical macro-steps are never reordered or run concurrently by this phase.
- A worker dispatch must never be able to create, resume, or reuse Store, receipt, lease, or grant state outside the existing FASE-002 coordinator-only primitives and this phase's own wave-lifecycle and concurrent-cap extensions to that Store schema.
- A capability grant scoped wider than the dispatched node's declared `files` must be rejected before the worker starts.
- Dispatch, observation, and recovery must never invoke a non-Claude runtime, perform convergence, resolve a conflict automatically, run independent review, or ship; when every Execution DAG node reaches a terminal state, `agent-execute` itself becomes terminal and the coordinator advances to `converge` as an ordinary macro-step dispatch under User Story 1, never performing convergence logic itself.
- A V2 work item, or a V3 work item without an admitted FASE-002 run, must reject a dispatch request without creating any wave, worker, or recovery state.
- The `agent-execute` leader's delegated coordinator authority (FR-016) must never outlive its own dispatch window: once its checkpoint is recorded, it holds no further authority to create leases, grants, or remediation records for that run.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST dispatch each of the eleven canonical macro-steps (specify, plan, checklist, tasks, analyze, agent-assign, agent-execute, converge, verify, review, ship) to exactly one Claude subagent leader, in that fixed order, and MUST NOT dispatch a macro-step until the previous one records `complete` through the existing checkpoint mechanism (ADR-0016); this phase never reorders, skips, or parallelizes macro-steps, and this rule has no exception — `agent-execute` receives its own single leader exactly like every other macro-step. A macro-step leader whose checkpoint records `blocked` instead of `complete` MUST halt the run — the coordinator MUST NOT dispatch any further macro-step until an operator resolves the block and the step is re-recorded `complete`; `blocked` is a real end state for that dispatch, but it is never treated as permission to advance. Within its own dispatch, the `agent-execute` leader is the one that runs User Story 2's wave loop (dispatching, observing, and remediating the Execution DAG's worker nodes) before submitting its own checkpoint receipt through the same unmodified attestation chain every other leader uses; no other macro-step's leader dispatches further subagents.
- **FR-002**: The system MUST invoke each macro-step's leader at no less than the floor the existing tier policy (`minimum_by_step`, recorded at FASE-001 activation, with an empty `promotions` list at the time of this phase) declares for that macro-step, resolving the exact canonical skill and registry hash pinned at activation, and MUST record the tier decision before dispatch without silently downgrading. The `agent-execute` leader's own tier (its `minimum_by_step` floor) and the tier of the Execution DAG nodes it dispatches (FR-006, resolved per node) are independent decisions — a leader legitimately orchestrates at a lower tier than a node it dispatches, since running the wave loop and producing a node's content are different skill demands.
- **FR-003**: The system MUST treat the Execution DAG produced by the `tasks` macro-step's own leader as the versioned artifact this phase validates and dispatches against; this phase MUST NOT generate or algorithmically derive a DAG through any other means.
- **FR-004**: While `agent-execute` is the current macro-step, the system MUST dispatch a worker only to an Execution DAG node whose declared dependencies are already terminal; a node declared `parallel:true` MAY share a wave with other eligible `parallel:true` nodes, and a node declared `parallel:false` MUST dispatch alone, with no other node of that run concurrently active. Parallelism MUST NOT be inferred beyond what the DAG explicitly declares. The system MUST fail closed — rejecting the entire Execution DAG before any `agent-execute` worker is dispatched — if any node's declared `files` contains an entry matching either of two independently-justified rules, evaluated on the full repo-relative path regardless of which directory it lives under (ADR-0018): (i) any path segment equal to `.specify` immediately followed by a segment equal to `reports` (i.e. a `.specify/reports/` directory appears anywhere in the path, at any depth) — producing verify, review, or ship evidence is those macro-steps' own work, and a `tasks` output naming such a path is malformed for `agent-execute` regardless of its `depends_on`, `tier`, or `parallel` value; or (ii) any path segment exactly equal to `.grill` (i.e. the path lives anywhere under a `.grill/` directory, at any depth) — this is the grill governance ledger's entire versioned control tree (state, decision records, ADRs, handoffs, audit and round-log evidence, the attestation campaign fields `checkpoint --step` itself reads and writes), and a dispatched `agent-execute` worker gaining write access to any file in it — not just the three files ADR-0018 originally named — would be able to alter or self-attest evidence about its own work product, the same self-approval risk `judge_checkpoint_attestation` exists to prevent for macro-step checkpoints (ADR-0016); the whole tree is out of scope for `agent-execute`, never a fixed enumeration of filenames within it. A DAG rejected under either rule halts the run exactly like any other malformed-DAG rejection (FR-014): correcting the offending `tasks` output is a manual action outside this phase's automatic scope, not a dead end this phase must resolve itself.
- **FR-005**: The system MUST NOT dispatch more workers concurrently for one run than its worker cap, where the effective cap is the lesser of the run's activation-configured cap and the Execution DAG's own declared `max_workers`. A stall-triggered replacement worker and a transient-failure retry each count against this same concurrent cap; a worker that reaches a terminal state frees its slot for a later wave.
- **FR-006**: The system MUST invoke each dispatched `agent-execute` worker as a native Claude subagent at the tier its Execution DAG node declares; that declared tier MUST be at or above the existing tier policy's `agent-execute` floor (`medium`) in the tier order `small < medium < large`, except a node whose declared files are exclusively Markdown MAY use the existing markdown-maintenance supplemental floor (`small`). Dispatch MUST block a node whose declared tier does not satisfy the applicable floor.
- **FR-007**: The system MUST create each `agent-execute` worker's lease and capability grant using the existing FASE-002 coordinator-only run/worker/lease/grant primitives before invoking it; the grant's scope MUST be exactly the dispatched node's declared `files` and MUST NOT be broader. Every worker's `worker_id` MUST be derived from its Execution DAG node's own `id` — the node's `id` verbatim for that node's first dispatch, and the same `id` with a distinguishing remediation suffix for any worker created to remediate it — so that node lineage is recoverable from `worker_id` alone; declared `files` MUST NOT be used to correlate node identity, since distinct nodes commonly declare identical `files` sets (the real Execution DAGs this phase consumes have the large majority of their nodes sharing a `files` set with at least one other node). Every Execution DAG node has exactly one automatic-remediation budget for its entire lifetime in a run, shared across FR-009 (stall replacement) and FR-010 (transient retry) — not one budget per mechanism. A worker created to remediate a prior worker of the same node, whether as a stall replacement (FR-009) or a transient-failure retry (FR-010), MUST have its lease's recovery budget created already spent (`recovery_count` set to its exhausted value, never the fresh default a first dispatch receives); this MUST hold regardless of which of the two mechanisms funded the earlier worker, so a node cannot alternate between stall and transient-failure remediation to chain more than one automatic replacement, and this rule MUST be enforced per FR-008(e) rather than rely solely on the dispatching leader constructing the request correctly. A remediation worker is otherwise a new worker record like any other and counts against the concurrent cap exactly as FR-005 states.
- **FR-008**: The system MUST extend the coordinator's own Store schema, per ADR-0012, ADR-0013, and ADR-0015, so that: (a) the worker-cap check counts only workers in a non-terminal state rather than the lifetime total of worker records; (b) a run can declare more than one wave over its lifetime, each with a distinct identity; (c) a wave already superseded by a later wave remains immutable, while the current wave may record its own state transitions; (d) a new coordinator-only primitive records a progress transition correlated to a worker's active lease and, on every such record, renews that lease's expiration by the same fixed duration as its original grant, so a worker producing genuine progress past the original lease window is never treated as expired; (e) a worker record's lease MUST NOT be created with a fresh (unspent) remediation budget if any other worker record already present in the run has a `worker_id` sharing the same Execution DAG node lineage per FR-007's derivation rule — that shared `worker_id` lineage, not declared grant scope, is this phase's node-identity correlation, since two independent nodes routinely declare identical `files` and a scope-based match would reject legitimate first dispatches — and the Store MUST reject such a mint rather than accept it and rely on the dispatching leader alone to have passed the correct value. This extension is coordinator-owned and MUST NOT grant a worker any new authority beyond what FASE-002 already denies it.
- **FR-009**: The system MUST define worker progress as any new coordinator-recorded transition correlated to that worker's active lease, recorded via the FR-008(d) primitive since dispatch or since its previous recorded transition. The system MUST treat a worker whose lease has recorded no such transition for the run's configured stall window (fifteen minutes, as recorded at FASE-001 activation) as stalled, subject to FR-007's shared per-node remediation budget: a node whose budget is already spent — whether by an earlier stall replacement or an earlier transient retry (FR-010) — MUST NOT receive a further automatic replacement even though the new failure is itself a stall. For a node whose budget is not yet spent, the system MUST automatically record a recovery-eligible condition against that budget — independent of, and never consuming or consumed by, FASE-002's run-level manual-resume budget (ADR-0015) — then replace that worker exactly once, spending the budget per FR-007's rule. Any further failure of that node after its budget is spent MUST block with a diagnostic reason instead of a second automatic remediation. This phase never automatically relaunches the run, which remains a separate FASE-002 manual-resume action.
- **FR-010**: The system MUST classify a failed worker's outcome against a declared, closed transient-failure classification limited to a process-level timeout or a transport-level dispatch failure that never reached the worker's Claude subagent; every other failure classification (including any validator, gate, or contract rejection) MUST NOT be treated as transient. The system MUST dispatch exactly one automatic retry only for a failure matching that classification, subject to FR-007's shared per-node remediation budget: a node whose budget is already spent — whether by an earlier stall replacement (FR-009) or an earlier transient retry — MUST NOT receive a further automatic retry even when the new failure itself matches the transient classification. Every non-transient failure, and any failure recurring after a node's one remediation, MUST block with a diagnostic reason instead of retrying.
- **FR-011**: The system MUST NOT invoke a non-Claude runtime (Codex, Hermes, or any other) as a dispatch target for any macro-step leader or `agent-execute` worker.
- **FR-012**: The system MUST NOT perform convergence, automatic conflict resolution, independent review, or ship actions from dispatch, observation, or recovery logic; when every Execution DAG node reaches a terminal state, `agent-execute` itself becomes terminal and the coordinator's next action is the ordinary FR-001 dispatch of `converge` as the next macro-step, never a convergence action performed by this phase.
- **FR-013**: The system MUST record one compact dispatch status event — distinct from FASE-004's later Run Status Events — for each macro-step dispatch, each `agent-execute` worker dispatch, completion, stall, recovery action, and retry, correlated to the existing FASE-002 run and wave identities plus the affected worker and lease where applicable.
- **FR-014**: The system MUST fail closed — blocking dispatch before creating any wave, worker, lease, or grant state — on a malformed, missing, or cyclic Execution DAG, an over-cap wave request, or a node with no honorable declared tier.
- **FR-015**: The system MUST preserve the current behavior of V2 work items and of the existing FASE-001/FASE-002 command surface; dispatch MUST be available only to an activated V3 work item with an admitted FASE-002 run, and every `agent-execute` worker MUST target only a Worker Worktree already prepared through the existing FASE-002 worker-preparation primitive.
- **FR-016**: The system MUST treat the `agent-execute` leader as a distinct actor class from the Execution DAG workers it dispatches (ADR-0019): for the duration of its own dispatch, and only for that duration, it holds the same coordinator-only authority the outer orchestrating session holds for every other macro-step — to create worker leases and capability grants (FR-007), record progress transitions and renew lease TTLs (FR-008(d)), and record remediation (FR-009, FR-010) for the workers it dispatches. This delegation MUST NOT grant the leader, or any worker it dispatches, any Store-write authority beyond what FASE-002 already permits coordinator actions (ADR-0006, ADR-0010); the leader itself MUST NOT hold a capability grant scoped to any dispatched worker's declared `files`, MUST NOT be counted as one of the run's concurrent `agent-execute` workers, and MUST NOT gain this authority outside its own `agent-execute` dispatch window.

### Key Entities *(include if feature involves data)*

- **Macro-Step Dispatch**: The single-leader, fixed-order invocation of one of the eleven canonical macro-steps; the unit User Story 1 governs.
- **Execution Wave**: One `agent-execute` dispatch round's bounded set of workers, identified distinctly from any prior wave of the same run, limited to the run's effective concurrent worker cap and to Execution DAG nodes whose dependencies are terminal and whose `parallel` declaration permits sharing that round.
- **Model Tier Decision**: The recorded tier a dispatched macro-step leader or `agent-execute` worker is invoked at, taken from the existing tier policy (for a macro-step leader) or the Execution DAG node's own declared tier (for a worker), and validated against the applicable floor.
- **Stall Recovery**: The coordinator's evaluation, against the run's configured stall window, of whether a worker's lease has recorded new progress; a positive stall finding automatically records a recovery-eligible condition against that Execution DAG node's own shared remediation budget (FR-007, ADR-0015 — independent of FASE-002's run-level manual-resume budget) and triggers exactly one worker replacement per node — never an automatic run relaunch, which stays a separate manual FASE-002 action.
- **Retry Classification**: The declared, closed set of failure conditions (process-level timeout, transport-level dispatch failure) eligible for exactly one automatic retry, counted against the same worker cap as any other active worker.
- **Dispatch Status Event**: The compact, coordinator-recorded event for a macro-step dispatch, worker dispatch, completion, stall, recovery, or retry, correlated to run/wave/worker/lease identity where applicable; distinct from FASE-004's Run Status Events.
- **Autonomous Run**: A run that advances through successive macro-step dispatches and, within `agent-execute`, successive waves, without human confirmation between them, bounded entirely by the FRs above; it never advances past `agent-execute`'s dispatch into convergence, review, or ship logic performed by this phase.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In every supported run, macro-steps dispatch in the fixed eleven-step order with zero scenarios where a macro-step starts before the previous one is terminal or where two macro-steps are concurrently active.
- **SC-002**: In every supported `agent-execute` wave, zero workers are dispatched to a node with a non-terminal dependency or with `parallel:false` alongside another concurrently active node of the same run; one hundred percent of dispatched nodes have all declared dependencies terminal at dispatch time.
- **SC-003**: In every supported run, the total number of concurrently active `agent-execute` workers — original dispatch, stall replacement, and transient retry combined — never exceeds the run's effective concurrent worker cap (1-5, the lesser of activation config and DAG declaration), and zero scenarios undercount a stall-replacement or retry worker against that cap.
- **SC-004**: One hundred percent of dispatched macro-step leaders and `agent-execute` workers run at their applicable declared tier, at or above the applicable policy floor, using the canonical skill and registry hash pinned at FASE-001 activation; zero silent downgrades or unpinned invocations occur in any supported scenario.
- **SC-005**: Every Execution DAG node stalling for the first time in a run receives exactly one automatic remediation action (a stall replacement or, on a later transient failure of the same node, nothing further — the budget is shared with FR-010), drawn from that node's own single remediation budget (ADR-0015); one hundred percent of any-further-failure scenarios on a node whose budget is already spent block with a diagnostic instead of a second automatic remediation, regardless of whether the first spend was a stall or a transient retry, and zero scenarios consume or are blocked by FASE-002's separate run-level manual-resume budget.
- **SC-006**: Only failures matching the declared transient classification (process-level timeout, transport-level dispatch failure) receive an automatic retry, and each receives exactly one; zero retries occur for non-transient or recurring failures.
- **SC-007**: Zero dispatch, observation, or recovery code path invokes a non-Claude runtime, convergence, automatic conflict resolution, independent review, or ship in any supported scenario, including when every Execution DAG node reaches a terminal state and `agent-execute` hands off to the ordinary dispatch of `converge`.
- **SC-008**: One hundred percent of dispatched `agent-execute` worker capability grants are scoped to exactly their node's declared `files`, with zero scenarios where a grant exceeds that declared scope.
- **SC-009**: Zero Execution DAG nodes whose declared `files` match either of FR-004's two closed rejection rules are ever dispatched as `agent-execute` workers; every DAG containing one is rejected before dispatch, in every supported scenario.
- **SC-010**: Zero workers are treated as expired or stalled while their lease has recorded a progress transition (FR-008(d)) within the current stall window; one hundred percent of recorded progress transitions renew the lease's expiration by its original fixed duration.
- **SC-011**: Zero leases of any kind — first dispatch or remediation — are minted with a fresh (unspent) budget for a node whose `worker_id` lineage (FR-007) already has a spent-budget sibling in the run; the Store rejects such a mint (FR-008(e)) in every supported scenario, not only when the dispatching leader constructs the request correctly. Two independent nodes sharing an identical declared `files` set never cause a false rejection of either node's own first dispatch.
- **SC-012**: The `agent-execute` leader never appears as one of the run's concurrent `agent-execute` workers, never holds a capability grant scoped to a dispatched worker's declared `files`, and holds no coordinator-only authority (FR-016) once its own checkpoint is recorded, in every supported scenario.

## Assumptions

- The FASE-001 activation boundary and the FASE-002 durable run/worker/lease/grant primitives are available and remain the sole authority for coordinator state; this phase adds macro-step dispatch, wave lifecycle, concurrent-cap accounting, observation, and bounded recovery as coordinator-owned extensions on top of them (ADR-0012, ADR-0013).
- The Execution DAG's node graph, `tier`, `parallel`, `files`, and `max_workers` fields are produced by the `tasks` macro-step's own leader dispatch, not by a separate generator this phase writes (ADR-0014); this phase validates and consumes that DAG within `agent-execute`.
- Convergence, conflict resolution, independent review, and ship remain FASE-004's responsibility and are out of scope here even when every `agent-execute` wave of a run completes cleanly; this phase's only action at that point is the ordinary FR-001 dispatch of `converge`.
- The run's stall window is the value recorded at FASE-001 activation (currently fixed at fifteen minutes); this phase reads that configured value rather than declaring a second constant.
- The transient-failure classification is closed to conditions the coordinator can observe without trusting worker-reported content: a process-level timeout or a transport-level dispatch failure that never reached the invoked Claude subagent. Any failure the subagent itself reports (validator, gate, or contract rejection) is never transient.
- "The coordinator" always spans the same deterministic core (admission, lease, grant, checkpoint attestation, cap/wave validation, recovery budget — never delegated, never granted to a worker) plus whichever actor currently holds delegated dispatch authority for the in-flight macro-step (ADR-0017, formalized as FR-016). For ten of the eleven macro-steps that actor is the outer orchestrating session directly. For `agent-execute`, that actor is its own dispatched leader, only for the duration of its own dispatch (FR-016) — the same subagent whose checkpoint receipt closes the step — which invokes and observes its Execution DAG worker wave (User Story 2) using the identical coordinator-only core primitives the outer session would use for any other macro-step, and records the periodic progress signal (FR-008(d)) the same way. No worker of any wave ever holds this authority, and the leader's own authority does not survive its own checkpoint. This phase's FRs describe required coordinator behavior; which actor is exercising it at a given moment, and the exact mechanics of that delegation, are `plan.md` HOW-level detail — but the delegation's existence, scope, and boundary are WHAT-level (FR-016) because they touch FASE-002's Evidence Boundary directly. No primitive in the existing coordinator-only core checks a caller's identity today (`prepare_worker` and its siblings accept `root`/`work_id`/`run_id`/`worker_id`/`scope_paths`/`admission`, nothing that authenticates who is calling); FR-016's authority statement is therefore a construction-time restriction on what the dispatch surface is built to do, not a runtime identity gate — `plan.md` should not go looking for a caller-identity check to add symmetrically with FR-008(e)'s Store-level correlation, which is a different kind of check (data shape, not caller identity).
- A macro-step leader's completion is accepted the same way every macro-step has been accepted since before this phase existed: a receipt verified by the existing `judge_checkpoint_attestation` chain (ADR-0016). This phase does not add a second verification layer, and does not add an exception, for any of the eleven macro-step leaders — `agent-execute` has a real dispatched leader like the other ten, so its single-invocation receipt fits the existing attestation contract without requiring a new schema shape or an aggregated multi-worker receipt.
